# 予約台帳

予約（`bookings`）と、その施術明細（`booking_services`）の規則をまとめます。コントラクトは `specs/operations/booking-operations.tsp` と `specs/models/booking.tsp`、テーブルは `bookings`、`booking_services`、`booking_status_histories` です。

予約台帳は、サロンが予約を入れて読むためのものです。管理者とサロンのスタッフが `/api/v1/bookings` で扱います。顧客のアカウントは、このルートを使えません。顧客は、自分の予約を `/api/v1/customers/me/bookings` で扱います。規則は [顧客が自分で入れる予約](#顧客が自分で入れる予約) にまとめます。

空き枠（`/api/v1/salons/{salonId}/available-slots`）は、同じコントラクトにある、台帳とは別のルートです。規則は [空き枠](#空き枠) にまとめます。

## 実装範囲

| オペレーション | 状態 |
|---|---|
| 台帳（`BookingCrud`）の一覧、作成、1 件の取得、更新、削除 | 実装済み |
| ステータスの操作（`BookingCrud` の確定、キャンセル、施術の開始、完了、無断キャンセルの記録） | 実装済み |
| 日時の変更（`BookingCrud` の `reschedule`） | 実装済み |
| 終わっていない予約が参照する顧客、スタッフ、サービス、サロンの削除を断る（それぞれの削除の規則） | 実装済み |
| 施術明細の追加、取得、削除（`BookingServiceCrud`） | 実装済み |
| 空き枠の一覧と確認（`AvailableSlotCrud`） | 実装済み（[空き枠](#空き枠)） |
| 顧客が自分で入れる予約、自分の予約の一覧、1 件の取得、キャンセル（`CustomerBookings`） | 実装済み（[顧客が自分で入れる予約](#顧客が自分で入れる予約)） |
| 顧客による日時の変更（`CustomerBookings` の `reschedule`） | 実装済み（[顧客による日時の変更](#顧客による日時の変更)） |

予約のコントラクト（`specs/operations/booking-operations.tsp`）のオペレーションは、すべて実装されています。

- 次のものは、ありません
  - 予約についての通知。予約の確定、変更、キャンセルと、来店の前のリマインドを、顧客にもサロンにも、メールなどで知らせません。画面が、予約の一覧を読んで示します。サーバーが送るメールは、認証とスタッフの招待のものだけです（[メール](./email.md)）
  - `reminderSent` と `reminderSentAt` を書くオペレーション。リマインドを送る仕組みのための列で、作成が false と null を書いたあと、変えるものがありません。レスポンスでは、いつも false と null です
  - ステータスの履歴（`booking_status_histories`）を読むオペレーション。ステータスを変えた人、時刻、キャンセルの理由は、操作のたびに記録しますが（[ステータスの操作](#ステータスの操作)）、コントラクトに、読むオペレーションがありません

## サロンが台帳に入れる予約は、サロンの判断

台帳に入れる予約と、その日時の変更、施術明細の追加について、システムが確かめるのは、データの整合だけです。

- 参照するもの（サロン、顧客、スタッフ、サービス）が存在し、スタッフとサービスが予約のサロンのものであること
- スタッフが、同時に受けられる数を超えて重ならないこと（[スタッフの占有](#スタッフの占有)）

次の設定は、サロンが「何を受け付けるか」を決めたもので、電話や店頭で受けた予約をスタッフが台帳に入れることを妨げません。台帳の作成でも、日時の変更でも、施術明細の追加でも確かめません。

- サロンの `isActive`、営業時間
- スタッフの `isActive`、`canReceiveBookings`、勤務スケジュール、ランク（サービスの `requiredStaffLevel`）
- サービスの `isActive`、`serviceStatus`、`allowOnlineBooking`、`maxBookingsPerDay`
- 顧客の `isActive`、`customerStatus`

これらは、顧客が予約できる枠を決める条件です。サロン、スタッフ、サービスの設定は、空き枠の一覧が適用します（[受け付けの設定](#受け付けの設定)）。顧客の設定は、顧客が自分で入れる予約が適用します（[顧客の状態](#顧客の状態)）。顧客が自分の予約を移すときも、移る先に、どちらも適用します（[顧客による日時の変更](#顧客による日時の変更)）。空き枠の確認は、台帳と同じく、どれも確かめません。顧客の好み設定（[顧客台帳](./customers.md#好み設定)）は、サーバーの判定には使いません。画面が、希望するスタッフを初期選択に使い、避けるスタッフを候補から外します。

過去の日時の予約も作成できます（来店のあとで記録する）。日時の変更も、過去の日時にできます。

## オペレーションと権限

| オペレーション | ルート | 許可 |
|---|---|---|
| 一覧 | `GET /api/v1/bookings` | `admin`（すべてのサロン）、サロンの `owner` / `manager` / `staff`（所属サロンの予約だけ） |
| 作成 | `POST /api/v1/bookings` | `admin`、本文の `salonId` のサロンの `owner` / `manager` / `staff` |
| 1 件の取得 | `GET /api/v1/bookings/{id}` | `admin`、予約のサロンの `owner` / `manager` / `staff` |
| 更新 | `PATCH /api/v1/bookings/{id}` | 同上 |
| 削除 | `DELETE /api/v1/bookings/{id}` | `admin`、予約のサロンの `owner` / `manager` |
| 確定 | `POST /api/v1/bookings/{id}/confirm` | `admin`、予約のサロンの `owner` / `manager` / `staff` |
| キャンセル | `POST /api/v1/bookings/{id}/cancel` | 同上 |
| 施術の開始 | `POST /api/v1/bookings/{id}/start` | 同上 |
| 完了 | `POST /api/v1/bookings/{id}/complete` | 同上 |
| 無断キャンセルの記録 | `POST /api/v1/bookings/{id}/no-show` | 同上 |
| 日時の変更 | `POST /api/v1/bookings/{id}/reschedule` | 同上 |
| 施術明細の追加 | `POST /api/v1/bookings/{bookingId}/services` | 同上 |
| 施術明細の取得 | `GET /api/v1/bookings/{bookingId}/services/{id}` | 同上 |
| 施術明細の削除 | `DELETE /api/v1/bookings/{bookingId}/services/{id}` | 同上 |

- すべてのオペレーションに認証が要ります
- 予約はサロンのものですが、ルートはサロンの下に置きません（コントラクトのとおり `/api/v1/bookings`）。サロンは、作成では本文の `salonId`、一覧ではクエリの `salonId`、ほかのオペレーション（取得、更新、削除、ステータスの操作、日時の変更、施術明細のオペレーション）では予約そのものが決めます
- 誰がどの予約に届くかは、操作者の範囲で決まります（`business-logic/booking/_shared/authorization.ts` の `bookingReachOf`）。`admin` はすべてのサロン、サロンのユーザーは所属サロンです
- サロンの 3 つのロールの違いは、予約の削除だけです。削除できるのは `owner` と `manager` で、`staff` には 403 を返します（同じファイルの `bookingRemovalReachOf`）。削除は、予約の履歴を消し、顧客の来店回数を変えるからです。スタッフは、行われない予約をキャンセルします。施術明細の削除は、履歴も来店回数も変えないので、`staff` にもできます
- **顧客のアカウントは、このルートを使えません**（403）。`BookingResponse` はサロン内のメモ（`internalNotes`）を含みます。顧客台帳と同じく、顧客には、自分の予約だけを、見せてよい項目だけで返す別のルートがあります（[顧客が自分で入れる予約](#顧客が自分で入れる予約)）。ロールに必要なレコードを持たないユーザー（範囲 `none`）も 403 です
- **ほかのサロンの予約は、存在しない予約と区別しません**。取得、更新、削除、ステータスの操作、日時の変更、施術明細のオペレーションは 404、一覧には出ず、カーソルに指定すると 400 です
- ID（パスの `id` と `bookingId`、本文とクエリの ID）は、英字を大文字で書いても同じ ID です。レスポンスの ID は小文字です
- レスポンスの `links` は `self` と `list` です。作成は 201 で、`Location` ヘッダーに予約の URL を返します。更新、ステータスの操作、日時の変更は 200 で、そのあとの予約を返します。削除は 204 で、本文はありません。施術明細のオペレーションのレスポンスは、[施術明細の追加と削除](#施術明細の追加と削除) にあります

### 確認の順序

作成:

1. アクセストークン（401）
2. 操作者の種類（403。顧客、範囲のないアカウント）
3. リクエストの本文（400）
4. 本文の `salonId` が操作者のサロンであること（403。`admin` はどのサロンでもよい）
5. 参照するものの存在（400。[参照するもの](#参照するもの)）
6. サロンのタイムゾーン（409。[来店日とサロンのタイムゾーン](#来店日とサロンのタイムゾーン)）
7. 金額の上限（400）
8. スタッフの占有（409）

一覧:

1. アクセストークン（401）
2. 操作者の種類（403）
3. クエリ（400）
4. クエリの `salonId` が操作者のサロンであること（403）
5. カーソル（400。操作者に見える予約を指していること）

取得:

1. アクセストークン（401）
2. 操作者の種類（403）
3. ID の形式（400）
4. 予約の存在（404。ほかのサロンの予約も同じ）

ステータスの操作:

1. アクセストークン（401）
2. 操作者の種類（403）
3. ID の形式（400）
4. リクエストの本文（400。本文があるのはキャンセルと完了）
5. 予約の存在（404。ほかのサロンの予約も同じ）
6. 予約のステータス（409）
7. 操作ごとの条件（409。無断キャンセルの記録は開始日時を過ぎていること、完了は実際の終了が開始より後であること）

更新:

1. アクセストークン（401）
2. 操作者の種類（403）
3. ID の形式（400）
4. リクエストの本文（400）
5. 予約の存在（404。ほかのサロンの予約も同じ）

日時の変更:

1. アクセストークン（401）
2. 操作者の種類（403）
3. ID の形式（400）
4. リクエストの本文（400）
5. 予約の存在（404。ほかのサロンの予約も同じ）
6. 予約のステータス（409）
7. 本文の `staffId` が、予約のサロンの、削除されていないスタッフであること（400）
8. サロンのタイムゾーン（409）
9. スタッフの占有（409）

削除:

1. アクセストークン（401）
2. 操作者の種類（403。顧客、範囲のないアカウント、サロンの `staff`）
3. ID の形式（400）
4. 予約の存在（404。ほかのサロンの予約も同じ）
5. 予約を参照する売上、施術記録、レビュー（409）

施術明細の追加:

1. アクセストークン（401）
2. 操作者の種類（403）
3. `bookingId` の形式（400）
4. リクエストの本文（400）
5. 予約の存在（404。ほかのサロンの予約も同じ）
6. 予約のステータス（409）
7. 明細の数（409）
8. すべての明細が 24 時間以内に始まること（409）
9. 本文の `serviceId` と `staffId` が、予約のサロンの、削除されていないものであること（400）
10. サロンのタイムゾーン（409）
11. 金額の上限（409）
12. スタッフの占有（409）

施術明細の取得:

1. アクセストークン（401）
2. 操作者の種類（403）
3. `bookingId` の形式、明細の `id` の形式（400。この順）
4. 予約と明細の存在（404。ほかのサロンの予約の明細、ほかの予約の明細も同じ）

施術明細の削除:

1. アクセストークン（401）
2. 操作者の種類（403）
3. `bookingId` の形式、明細の `id` の形式（400。この順）
4. 予約の存在（404。ほかのサロンの予約も同じ）
5. その予約の明細であること（404）
6. 予約のステータス（409）
7. 最後の明細でないこと（409）
8. サロンのタイムゾーン（409）
9. 金額の上限（409）

顧客のアカウントには、本文やクエリや ID が不正でも 403 を返します。サロンのユーザーがほかのサロンの `salonId` を指定したときは、本文（またはクエリ）が正しければ 403 で、不正なら 400 です。どのサロンかは、本文を読まないと分からないからです。

読めない本文（400 のコード `2002`、415、413）は、この順序の前に答えます（[顧客台帳の確認の順序](./customers.md#確認の順序) と同じ）。

## 作成リクエストの規則

`BookingCreateRequest` は全項目が必須で、null にできるのは、型に `null` がある項目だけです。表にない項目を書くと 400（`unrecognized_keys`）です。

| 項目 | 型 | 規則 |
|---|---|---|
| `salonId` | `SalonId` | 削除されていないサロン |
| `customerId` | `CustomerId` | 削除されていない顧客 |
| `staffId` | `StaffId` | 予約の担当スタッフ。`salonId` のサロンの、削除されていないスタッフ |
| `depositAmount` | `int32 \| null` | 0 以上、2,147,483,647 以下 |
| `customerRequest` | `string \| null` | 空白だけでない |
| `internalNotes` | `string \| null` | 空白だけでない |
| `source` | `string \| null` | 空白だけでない、50 文字以内 |
| `services` | 施術明細の一覧 | 1 件以上 20 件以下 |
| `services[].serviceId` | `ServiceId` | `salonId` のサロンの、削除されていないサービス |
| `services[].staffId` | `StaffId \| null` | `salonId` のサロンの、削除されていないスタッフ。null は「担当を決めない」 |
| `services[].startTime` | `utcDateTime` | UTC（`Z`）で、分単位（秒と小数は 0） |
| `services[].notes` | `string \| null` | 空白だけでない |

- すべての明細は、最も早い明細の開始から 24 時間以内に始まります（400。`services.<番号>.startTime`）。予約は 1 回の来店で、1 日後に始まる明細は日付の打ち間違いだからです
- 同じサービスを 2 つの明細に指定できます（2 人分、2 回分）。明細の時間が互いに重なってもかまいません（2 人のスタッフが同時に施術する）
- 明細は、リクエストに書いた順に並びます（`sortOrder` は 0 から）。開始日時の順である必要はありません
- 本文だけで分かる誤りは、1 回の応答ですべて挙げます

### 参照するもの

- 存在しない、削除されている、`salonId` のサロンのものでない、のどれも 400 で、区別しません（`rule` は `not_found`）。`field` は `salonId`、`customerId`、`staffId`、`services.<番号>.serviceId`、`services.<番号>.staffId` です
- 1 回の応答で、見つからなかったものをすべて挙げます。サロンが見つからないときは、スタッフとサービスは確かめません（サロンと顧客だけを挙げます）。属するサロンがなければ、スタッフもサービスも探せないからです
- 予約の担当スタッフ（`staffId`）と明細のスタッフ（`services[].staffId`）は別の項目です。担当スタッフが、どの明細も担当しなくてもかまいません

## システムが決める値

リクエストが書くのは、誰の予約か、どのサービスをいつ始めるか、だけです。ほかの値は、参照する行から、作成の時点で決まります（`business-logic/booking/_shared/plan.ts` の `planBooking`）。あとから追加する明細の値は、追加の時点で、同じ規則で決まります（[施術明細の追加と削除](#施術明細の追加と削除)）。

明細（`booking_services`）:

| カラム | 値 |
|---|---|
| `duration` | サービスの `duration` |
| `endTime` | `startTime` + `duration` 分 |
| `price` | サービスの `price` |
| `discountAmount` | `price` − `discountPrice`（`discountPrice` が null なら 0） |
| `finalPrice` | `price` − `discountAmount` |
| `taxIncluded` | サービスの `taxIncluded`（料金が消費税を含むかどうか） |
| `sortOrder` | リクエストの順（0 から）。あとから追加する明細は、最後の明細の次 |
| `isCompleted`、`completedAt` | false、null |

予約（`bookings`）:

| カラム | 値 |
|---|---|
| `bookingNumber` | [予約番号](#予約番号) |
| `status` | `pending` |
| `startTime`、`endTime` | 明細の最も早い開始、最も遅い終了 |
| `duration` | `startTime` から `endTime` までの分数 |
| `bookingDate` | `startTime` を、サロンのタイムゾーンで表した日付 |
| `subtotal` | 明細の `price` の合計 |
| `discountAmount` | 明細の `discountAmount` の合計 |
| `taxAmount` | [消費税](#消費税) |
| `totalAmount` | `subtotal` − `discountAmount` + `taxAmount` |
| `pointsUsed`、`pointsEarned`、`cancellationFee` | null（`cancellationFee` は、キャンセルで 0 になる） |
| `reminderSent`、`reminderSentAt` | false、null |
| `cancelledAt`、`cancelledBy`、`cancellationReason`、`completedAt`、`actualStartTime`、`actualEndTime` | null（[ステータスの操作](#ステータスの操作) が書く） |
| `ipAddress`、`userAgent` | リクエストの送信元（監査用。レスポンスには出さない） |

- 明細の金額と時間、料金が消費税を含むかどうかは、明細を入れた時点のサービスの写しです。あとでサービスの料金や所要時間、税込かどうかを変えても、予約は変わりません
- 予約の日時と金額は、明細から算出します（`business-logic/booking/_shared/summary.ts` の `summarize`）。作成と、明細の追加と削除が、同じ関数で算出します。金額の規則（`business-logic/_shared/amounts.ts` の `amountsOf`）は、売上の金額の計算と共有します（[売上台帳](./sales.md#金額の計算)）
- `subtotal` か `totalAmount` が `integer` の上限（2,147,483,647）を超える予約は 400 です（`services` の `too_big`）
- 明細の間に空き時間があっても、予約の `duration` は最初の開始から最後の終了までの分数です。明細の `duration` の合計とは限りません
- ステータスの履歴（`booking_status_histories`）に、作成を 1 行書きます（`fromStatus` が null、`toStatus` が `pending`、`changedBy` が操作者のユーザー ID）。ステータスの操作も、1 回につき 1 行書きます。更新と、台帳での日時の変更は、ステータスを変えないので、履歴を書きません。顧客による日時の変更は、確定済みの予約を確定待ちに戻すときに、1 行書きます（[顧客による日時の変更](#顧客による日時の変更)）。履歴を読むオペレーションはありません

### 消費税

- 税込価格のサービス（`taxIncluded` が true。既定値）は、料金に消費税を含みます。`taxAmount` には加えません
- 税抜価格のサービス（`taxIncluded` が false）には、サロンの税率（`salons.taxRate`）で消費税を加えます。`taxAmount` は、税抜価格の明細の `finalPrice` の合計 × 税率で、1 円未満は切り捨てます
- 税込かどうかは、明細が写しを持ちます（`booking_services.taxIncluded`。レスポンスの明細にも出る）。明細を入れたあとでサービスの設定を変えても、その明細の扱いは変わりません
- 税率は、算出の時点のサロンの税率です（予約は税率を持ちません）。明細を追加、削除すると、予約の消費税を、その時点の税率で、残るすべての明細について算出し直します。作成のあとで税率が変わっていれば、新しい税率になります
- 端数の処理は、予約ごとに 1 回です（明細ごとに丸めて合計しません）。適格請求書の消費税額の端数処理の単位（消費税法基本通達 1-8-15: 一の適格請求書につき、税率の異なるごとに 1 回）に合わせています。この API のサロンは税率を 1 つ持ちます
- つまり `taxAmount` は「料金に加える消費税」で、税込価格に含まれている分は入りません
- 計算は整数で行います（税率を 100 分の 1 パーセント単位の整数にして掛ける）。浮動小数点の誤差で 1 円ずれることはありません

### 予約番号

- `BK-XXXX-XXXX` の形式です。`X` は、数字と、読み間違えやすい文字（I、L、O、U）を除いた英大文字の 32 文字（Crockford の Base32 の文字集合）から、暗号論的な乱数で選びます（32^8 ≒ 1.1 × 10^12 通り）
- 連番にはしません。連番は、プラットフォーム全体の予約の件数を、番号を見た人に伝えます
- すでにある番号と重なったら、別の番号で作り直します（一意制約 `bookings_booking_number_unique`）。3 回続けて重なると 500 です
- 番号を作るのは `business-logic/booking/_shared/booking-number.ts` の `bookingNumberFrom`、乱数を渡すのは `infrastructure` の `RandomBookingNumberIssuer` です。形式そのもの（`business-logic/_shared/record-number.ts` の `recordNumberFrom`）は、売上番号と共通です

### 来店日とサロンのタイムゾーン

- `bookingDate` は、`startTime` をサロンのタイムゾーン（`salons.timezone`）で表した日付です。日本時間の 0:30 に始まる予約は、UTC では前日でも、来店日はその日です
- サロンの `timezone` は、タイムゾーンの名前でなければなりません（サロンの作成と更新で 400）。実行環境が名前として知っているもの（`Asia/Tokyo`、`UTC` など）を受け付け、`+09:00` のようなオフセットは受け付けません。オフセットは、いまの時計のずれを表すだけで、夏時間のある地域では季節によって変わるからです（`schemas/rules.ts` の `timeZoneName`）
- この規則より前に保存されたサロンが、名前として読めないタイムゾーンを持っていると、来店日を決められません。そのサロンへの予約の作成と、そのサロンの予約の日時の変更は 409 です（`detail` が、サロンのタイムゾーンを直すよう伝える）。以前に保存されたオフセット（`+09:00`）は、日付を決められるので、そのまま使います
- サロンの営業時間（曜日ごとの `businessHours` と、営業日カレンダーの `openingHours`）と、スタッフの勤務スケジュールの時刻も、サロンの `timezone` での、その日の時刻です。どれも、自分のタイムゾーンを持ちません。曜日ごとの営業時間は、以前、1 件ごとに `timezone` を持っていました。サロンの `timezone` と食い違う値を保存でき、読むコードもなかったので、コントラクトから除きました（送ると 400）。保存されていた値からは、マイグレーション `202611160500_business_hours_without_time_zone.sql` が除きます

## スタッフの占有

- 予約は、明細を担当するスタッフ（`booking_services.staffId`）を、その明細の時間だけ占有します。前後に、スタッフの準備時間（`bufferTimeBefore`）と片付け時間（`bufferTimeAfter`）を加えます: `startTime − bufferTimeBefore` から `endTime + bufferTimeAfter` まで（終わりの時刻は含まない）
- **担当を決めていない明細（`staffId` が null）は、誰も占有しません**。予約の担当スタッフ（`bookings.staffId`）も、明細を担当していない時間は占有されません（カラーの放置時間に、ほかの顧客を担当できる）
- 占有するのは、ステータスが `cancelled` と `no_show` 以外の予約です（`draft`、`pending`、`confirmed`、`in_progress`、`completed`）。キャンセルした予約と、無断キャンセルを記録した予約は、その時点から誰も占有しません。確定しても、占有は変わりません（作成の時点から占有している）
- どの時点でも、1 人のスタッフを占有する予約の数は、そのスタッフの `maxConcurrentBookings` を超えません。超える予約の作成と、超える日時への変更、超える明細の追加は 409 です（`detail` に、空いていないスタッフの ID が入る）
- 日時の変更では、その予約自身の、変更前の明細は数えません。30 分だけ後ろにずらす変更が、自分自身と重なることはありません
- 明細の追加で確かめるのは、追加する明細のスタッフだけです。その予約がすでに持つ明細は数えません
- 1 つの予約の中の複数の明細が同じスタッフを同じ時間に占有しても、1 件と数えます
- 準備時間と片付け時間は、確認の時点のスタッフの設定を使います（予約には写しません）。両方の予約に同じ設定を当てはめます。設定を変えても、すでにある予約は見直しません
- 同じ顧客の予約どうしの重なりは確かめません

規則は `business-logic/booking/_shared/occupancy.ts` の `isOccupiedBeyondCapacity` です。

## ステータスの操作

予約のステータスは、5 つの操作で変えます。更新（`PATCH`）のリクエストに `status` はありません。

| 操作 | 操作できるステータス | 操作のあと | 本文 |
|---|---|---|---|
| 確定（`confirm`） | `draft`、`pending` | `confirmed` | なし |
| キャンセル（`cancel`） | `draft`、`pending`、`confirmed` | `cancelled` | `BookingCancelRequest` |
| 施術の開始（`start`） | `confirmed` | `in_progress` | なし |
| 完了（`complete`） | `confirmed`、`in_progress` | `completed` | `BookingCompleteRequest` |
| 無断キャンセルの記録（`no-show`） | `pending`、`confirmed` | `no_show` | なし |

- 表にないステータスの予約への操作は 409 です。`detail` に、いまのステータスと、操作できるステータスが入ります
- `completed`、`cancelled`、`no_show` からは、どこにも進みません。誤って閉じた予約は、削除して入れ直します（[削除](#削除)）
- 操作のほかにステータスを変えるのは、顧客による日時の変更だけです。確定済み（`confirmed`）の予約を、顧客が別の日時か別のスタッフに移すと、`pending` に戻ります（[顧客による日時の変更](#顧客による日時の変更)）。台帳での日時の変更は、ステータスを変えません
- 作成した予約は `pending` です。`draft` の予約を作るオペレーションはありませんが、`draft` の行があれば、確定とキャンセルができます
- 施術を始めた予約（`in_progress`）は、キャンセルも、無断キャンセルの記録もできません。顧客は来店しています
- 開始を記録せずに、`confirmed` から完了にできます（開始の記録は任意）
- 規則は `business-logic/booking/_shared/status.ts` の `planStatusChange` です。どの操作も、ステータスの履歴に 1 行書きます（`fromStatus`、`toStatus`、`changedBy`。`reason` はキャンセルの理由で、ほかの操作では null）
- 日時は、データベースの時計で決めます。予約の行をロックできた時点の時刻（`clock_timestamp()`）です。アプリケーションサーバーの時計も、トランザクションの開始時刻（`now()`）も使いません。`now()` は、ほかの操作を待つ前の時刻で、それを書くと、あとから書いた操作が、先に書いた操作より前の時刻を残すことがあるためです
- 同じ予約への操作は、書いた順に、後の時刻を書きます。ステータスの履歴は、`createdAt` の順が、変更の順です
- 本文のない操作（確定、施術の開始、無断キャンセルの記録）に本文を送っても、内容は見ません。JSON として読めない本文は、ほかのルートと同じく 400 です

### 各操作が書く値

| 操作 | 書く値 |
|---|---|
| 確定 | `status` だけ |
| キャンセル | `cancelledAt`（操作の日時）、`cancelledBy`（操作者のユーザー ID）、`cancellationReason`（本文の値）、`cancellationFee`（0） |
| 施術の開始 | `actualStartTime`（操作の日時） |
| 完了 | `completedAt`（操作の日時）、本文の `actualStartTime`・`actualEndTime` のうち null でないもの。まだ完了していない明細の `isCompleted`（true）と `completedAt`（操作の日時） |
| 無断キャンセルの記録 | `status` だけ |

どの操作も、予約の `updatedAt` を更新します。

### キャンセル

| 項目 | 型 | 規則 |
|---|---|---|
| `cancellationReason` | `string \| null` | 空白だけでない。null は「理由を記録しない」 |

- 開始日時の前でも後でも、キャンセルできます。来店しないと連絡があった予約は、開始日時を過ぎていてもキャンセルです。顧客が自分でキャンセルできるのは、開始日時より前だけです（[顧客によるキャンセル](#顧客によるキャンセル)）
- **キャンセル料（`cancellationFee`）は、常に 0 です**。料金を決める規則（何日前から、何パーセントか）が定義されていないからです。規則を持つカラムもありません（形式の決まっていなかった `salons.cancellationPolicy` は、#233 で削除しました）
- いつ、誰がキャンセルしたかは、システムが書きます。本文に `cancelledAt`、`cancelledBy`、`cancellationFee` を書くと 400（`unrecognized_keys`）です

### 施術の開始と完了

| 項目 | 型 | 規則 |
|---|---|---|
| `actualStartTime` | `utcDateTime \| null` | UTC（`Z`）で、UTC の日付で 1900-01-01 から 2999-12-31 まで。null は「記録済みの値を残す」 |
| `actualEndTime` | `utcDateTime \| null` | UTC（`Z`）で、UTC の日付で 1900-01-01 から 2999-12-31 まで。null は「記録済みの値を残す」 |

- 施術の開始は、`actualStartTime` に操作の日時を書きます。予約の開始日時より前でも、開始できます（早く来店した顧客）
- 完了は、本文の `actualStartTime` と `actualEndTime` のうち、null でないものを書きます。null の項目は、予約に記録済みの値を残します。開始を記録した予約を `{"actualStartTime": null, "actualEndTime": "…"}` で完了すると、開始は記録したままで、終了だけを書きます
- 完了しても、`actualEndTime` に操作の日時は入りません。本文に書かなければ null のままです（完了を登録した日時は `completedAt`）
- 実際の日時は、ミリ秒まで保存します（予約の日時と違い、分単位に限りません）。予約の日時や現在の日時との前後は確かめません（あとから記録できる）
- 実際の終了は、実際の開始より後でなければなりません。本文の 2 つの値がこれを満たさなければ 400（`actualEndTime` の `custom`）、本文の値と記録済みの値がこれを満たさなければ 409 です（リクエストだけでは分からない誤りで、両方の日時を送れば直せる）
- 完了は、予約のすべての明細を完了にします。明細を 1 つずつ完了にするオペレーションはありません

### 無断キャンセルの記録

- 顧客が、連絡なしに来店しなかったことを記録します
- **予約の開始日時（`startTime`）を過ぎるまでは、記録できません**（409）。まだ始まっていない予約に、来なかった顧客はいません。来ないと分かった予約は、キャンセルします
- 開始日時ちょうどから、記録できます。猶予の時間（開始の何分後から、など）は定義しません。サロンが判断します

### 顧客の来店回数

顧客の次の 5 つの値は、その顧客の予約から数えます（[顧客台帳](./customers.md#予約から数える値)）。

| カラム | 値 |
|---|---|
| `visitCount` | `completed` の予約の数 |
| `cancellationCount` | `cancelled` の予約の数 |
| `noShowCount` | `no_show` の予約の数 |
| `firstVisitDate`、`lastVisitDate` | `completed` の予約の来店日（`bookingDate`）の、最も早い日と最も遅い日。来店がなければ null |

- 完了、キャンセル、無断キャンセルの記録は、同じトランザクションの中で、顧客の 5 つの値を数え直します（1 を加えるのではなく、予約から数える）。確定と施術の開始は、数え直しません
- `completed`、`cancelled`、`no_show` の予約の削除も、同じように数え直します（[削除](#削除)）。更新と日時の変更は、数える値を変えないので、数え直しません
- 数えるのは、すべてのサロンの予約です。顧客はプラットフォームに 1 人で、サロンごとの値は持ちません
- 削除された顧客（`deletedAt`）の予約も、ステータスを変えられます。値も数え直します

## 更新

`PATCH /api/v1/bookings/{id}` は、サロンが予約に書き留める 4 つの項目を変えます。

| 項目 | 型 | 規則 |
|---|---|---|
| `depositAmount` | `int32 \| null` | 0 以上、2,147,483,647 以下 |
| `customerRequest` | `string \| null` | 空白だけでない |
| `internalNotes` | `string \| null` | 空白だけでない |
| `source` | `string \| null` | 空白だけでない、50 文字以内 |

- 規則は、作成の同じ項目と同じです（スキーマは、同じ定義から作る）
- どの項目も省略でき、1 つ以上を指定します。何も指定しないと 400 です（リクエスト全体の `custom`）。指定した項目だけを書き、省略した項目は変えません。null は「値を消す」です
- 表にない項目を書くと 400（`unrecognized_keys`）です。ステータス（`status`）は [ステータスの操作](#ステータスの操作) で、開始日時と担当スタッフ（`startTime`、`staffId`）は [日時の変更](#日時の変更) で変えます。サロン、顧客、予約番号、金額、施術明細は変えられません
- どのステータスの予約も更新できます。来店のあとで、メモを書き足せます
- 書くのは、指定した項目と `updatedAt` だけです。ステータスの履歴は書かず、顧客の回数も数え直しません

## 日時の変更

`POST /api/v1/bookings/{id}/reschedule` は、予約の開始日時と担当スタッフを変えます。顧客が自分の予約を移すルートは、別にあります（[顧客による日時の変更](#顧客による日時の変更)）。そちらは、移る先が空き枠であることを確かめます。

| 項目 | 型 | 規則 |
|---|---|---|
| `startTime` | `utcDateTime` | 新しい開始日時。UTC（`Z`）で、分単位（秒と小数は 0）。UTC の日付で 1900-01-01 から 2999-12-31 まで |
| `staffId` | `StaffId` | 新しい担当スタッフ。予約のサロンの、削除されていないスタッフ |

- 2 つとも必須です。担当スタッフを変えないときは、いまの担当スタッフを書きます。表にない項目を書くと 400（`unrecognized_keys`）です
- 変更できるのは、`draft`、`pending`、`confirmed` の予約です。ほかのステータスの予約は 409 です（`detail` に、いまのステータスと、変更できるステータスが入る）。施術を始めた予約と、閉じた予約は動かしません
- 予約の `startTime` を本文の値にして、予約の `endTime` と、すべての明細の `startTime`・`endTime` を、同じ時間だけずらします。前にも後ろにも動かせます。明細の順序、間隔、所要時間は変わりません
- 予約の `staffId` を本文の値にして、**変更前の担当スタッフが担当していた明細を、新しい担当スタッフに付け替えます**。ほかのスタッフが担当する明細と、担当を決めていない明細（`staffId` が null）は、そのままです。明細ごとにスタッフを変えるには、新しい明細を追加して、古い明細を削除します（[施術明細の追加と削除](#施術明細の追加と削除)）
- `staffId` が、存在しない、削除されている、予約のサロンのものでない、のどれも 400 で、区別しません（`staffId` の `not_found`）。いまの担当スタッフが削除されていれば、そのスタッフを書いても 400 です（ほかのスタッフに替える）。本文が書かないスタッフ（明細を担当したままのスタッフ）は、削除されていても断りません。終わっていない予約のスタッフは削除できないので（[予約が参照するものの削除](#予約が参照するものの削除)）、どちらも、その規則より前に削除されたスタッフの場合です
- `bookingDate` は、新しい `startTime` をサロンのタイムゾーンで表した日付にします（[来店日とサロンのタイムゾーン](#来店日とサロンのタイムゾーン)）
- [スタッフの占有](#スタッフの占有) を、作成と同じ規則で確かめます。変更後の明細を担当するスタッフ（付け替えた明細のスタッフも、そのままの明細のスタッフも）が、同時に受けられる数を超えてほかの予約と重なると 409 です
- 確かめるのは、作成と同じく、データの整合だけです。営業時間、勤務スケジュール、過去の日時かどうかは確かめません
- ステータス、`duration`、金額、明細のサービスと料金は変わりません。ステータスの履歴は書かず、顧客の回数も数え直しません
- 同じ日時と同じ担当スタッフへの変更も 200 です（`updatedAt` だけが変わる）
- 規則は `business-logic/booking/_shared/reschedule.ts` です。`moveBooking` が、動かせるステータスかを決めて、動かしたあとの予約と明細を作り、`planReschedule` が、担当スタッフとタイムゾーンを確かめて、書く行を決めます

## 施術明細の追加と削除

予約の施術明細は、作成のあとでも足し、外せます（`BookingServiceCrud`）。メニューを足す、やめる、明細の担当スタッフを替える、のための操作です。

| オペレーション | ルート | 成功 |
|---|---|---|
| 追加 | `POST /api/v1/bookings/{bookingId}/services` | 201。追加した明細。`Location` ヘッダーに明細の URL |
| 取得 | `GET /api/v1/bookings/{bookingId}/services/{id}` | 200。明細 |
| 削除 | `DELETE /api/v1/bookings/{bookingId}/services/{id}` | 204。本文はない |

- **明細を変えられるのは、終わっていない予約です**（`draft`、`pending`、`confirmed`、`in_progress`）。`completed`、`cancelled`、`no_show` の予約への追加と削除は 409 です（`detail` に、いまのステータスと、変えられるステータスが入る）。行われたこと、行われなかったことは、書き換えません
- 来店中（`in_progress`）の予約にも、明細を足し、外せます。施術の途中でメニューを足すのは、日常の操作だからです。日時の変更（来店が始まった予約は動かさない）とは、ここが違います。[予約が参照するものの削除](#予約が参照するものの削除) の「終わっていない予約」と同じ集合で（`UNFINISHED_STATUSES`）、参照するものを削除できない間が、明細を変えられる間です
- 取得は、どのステータスの予約の明細も読めます
- 明細の一覧はありません（予約の取得が、明細を返します）。明細の更新もありません（コントラクトにない）。**明細の担当スタッフや開始日時を変えるには、新しい明細を追加してから、古い明細を削除します**
- パスの `id` は明細の ID です。その予約のものでない明細の ID は、存在しない明細と区別しません（404）
- レスポンスの `links` は、`self`（明細）と `booking`（予約）です。パスは、リクエストが書いたとおりに返します

### 明細の追加

本文は `BookingServiceCreateRequest` で、作成リクエストの `services[]` の 1 件と同じ形、同じ規則です（スキーマは、同じ定義）。全項目が必須で、表にない項目を書くと 400（`unrecognized_keys`）です。

| 項目 | 型 | 規則 |
|---|---|---|
| `serviceId` | `ServiceId` | 予約のサロンの、削除されていないサービス |
| `staffId` | `StaffId \| null` | 予約のサロンの、削除されていないスタッフ。null は「担当を決めない」 |
| `startTime` | `utcDateTime` | UTC（`Z`）で、分単位（秒と小数は 0）。UTC の日付で 1900-01-01 から 2999-12-31 まで |
| `notes` | `string \| null` | 空白だけでない |

- 明細の時間と金額、料金が消費税を含むかどうかは、**追加の時点のサービスの写し**です（[システムが決める値](#システムが決める値)。作成と同じ）。あとでサービスを変えても、明細は変わりません
- `sortOrder` は、いまの最後の明細の次です。削除で空いた番号は詰めません
- 予約の明細は 20 件までです（作成と同じ上限）。21 件目の追加は 409 です
- すべての明細は、最も早い明細の開始から 24 時間以内に始まります（作成と同じ規則を、追加したあとの明細に当てはめる）。満たさない追加は 409 です。作成では 400 ですが、追加では、本文だけでは分からない誤りだからです
- `serviceId`、`staffId` が、存在しない、削除されている、予約のサロンのものでない、のどれも 400 で、区別しません（`rule` は `not_found`）。両方が見つからなければ、1 回の応答で両方を挙げます
- [スタッフの占有](#スタッフの占有) を、作成と同じ規則で確かめます（409）。確かめるのは、追加する明細のスタッフだけです。この予約がすでに持つ明細は数えません（1 つの予約の中の明細は、1 件と数える）
- 確かめるのは、作成と同じく、データの整合だけです。営業時間、勤務スケジュール、過去の日時かどうかは確かめません

### 明細の削除

- 予約に残る最後の明細は削除できません（409）。明細のない予約は作れないのと同じです。行われない予約は、キャンセルします
- 削除した明細が占有していた時間は、空きます
- サロンの `staff` も削除できます（[オペレーションと権限](#オペレーションと権限)）
- 本文は見ません。JSON として読めない本文は、ほかのルートと同じく 400 です

### 予約の算出し直し

追加と削除は、同じトランザクションの中で、予約の次の値を、残る明細から算出し直します。

| カラム | 値 |
|---|---|
| `startTime`、`endTime`、`duration` | 明細の最も早い開始、最も遅い終了、その間の分数 |
| `bookingDate` | `startTime` を、サロンのタイムゾーンで表した日付 |
| `subtotal`、`discountAmount` | 明細の `price`、`discountAmount` の合計 |
| `taxAmount` | 税抜価格の明細の `finalPrice` の合計 × サロンの税率（[消費税](#消費税)） |
| `totalAmount` | `subtotal` − `discountAmount` + `taxAmount` |

- 算出の規則は、作成と同じ 1 つの関数です（`business-logic/booking/_shared/summary.ts` の `summarize`）
- 最も早い明細より前に始まる明細を足すと、予約の開始が早まり、来店日が変わることがあります。最も早い明細を外したときも同じです
- 税率は、明細を変えた時点のサロンの税率です。作成のあとで税率が変わっていれば、残る明細の消費税も、新しい税率になります
- サロンのタイムゾーンが名前として読めないときは 409 です（作成、日時の変更と同じ）。金額が `integer` の上限を超えるときも 409 です（税率が上がったあとの削除でも起こりうる）
- 担当スタッフ（`bookings.staffId`）、ステータス、メモは変わりません。ステータスの履歴は書かず、顧客の回数も数え直しません。`updatedAt` は変わります
- 規則は `business-logic/booking/_shared/service-lines.ts` の `planServiceAddition` と `planServiceRemoval` です

## 削除

`DELETE /api/v1/bookings/{id}` は、台帳にあるべきでない予約（誤って入れた予約、重複した予約）を取り除きます。行を残して隠す削除ではありません（`bookings` に `deletedAt` はない）。行われない予約は、削除ではなく、キャンセルします。

- 削除できるのは、`admin` と、予約のサロンの `owner`・`manager` です（[オペレーションと権限](#オペレーションと権限)）
- どのステータスの予約も削除できます
- 予約とともに、施術明細とステータスの履歴が消えます（外部キーの `ON DELETE CASCADE`）
- **売上（`sales`）、施術記録（`treatment_records`）、レビュー（`reviews`）のどれかが参照している予約は、削除できません**（409。`detail` に、何が参照しているかが入る。たとえば `The booking cannot be deleted: a sale, a treatment record and a review refer to it`）。行われた来店の記録だからです。レビューは顧客の声なので、予約と一緒に消せないようにします（[レビュー](./reviews.md#予約の削除)）。レビューを書いた顧客本人か `admin` がレビューを削除すれば、予約を削除できます。レビューの外部キーは `ON DELETE CASCADE` ですが、リポジトリが先に探して、削除を断ります。取り消した売上（`isVoid`）も、参照に数えます。売上は、売上台帳の作成が書き、更新が、指す予約を変えます（[売上台帳](./sales.md)）。施術記録は、施術中か完了の予約に、施術記録の作成が書きます。施術記録を削除すれば（`admin`、サロンの `owner` か `manager`）、予約を削除できます（[施術記録](./treatments.md#削除)）
- `completed`、`cancelled`、`no_show` の予約を削除したときは、同じトランザクションの中で、顧客の 5 つの値を数え直します（[顧客の来店回数](#顧客の来店回数)）。ほかのステータスの予約は、数えられていないので、数え直しません
- 削除した予約が占有していた時間は、空きます
- 成功は 204 で、本文はありません。削除した予約への取得、更新、ステータスの操作、日時の変更、2 度目の削除は 404 です
- 本文は見ません。JSON として読めない本文は、ほかのルートと同じく 400 です

## 予約が参照するものの削除

終わっていない予約が参照しているサロン、顧客、スタッフ、サービスは、削除できません（409）。予約のオペレーションではなく、それぞれの削除（顧客台帳、スタッフ台帳、サービス、サロン）の規則です。

- **終わっていない予約**は、ステータスが `draft`、`pending`、`confirmed`、`in_progress` の予約です。ステータスの操作が、まだ先へ進められる予約です（`business-logic/booking/_shared/status.ts` の `UNFINISHED_STATUSES`。遷移の表から導く）。`completed`、`cancelled`、`no_show` の予約は、いくつあっても削除を妨げません
- 来店日が過去でも、終わっていない予約は妨げます。閉じ忘れた予約を、完了、キャンセル、無断キャンセルの記録、削除のどれかで片付けてから、削除します

| 削除 | 妨げる予約 |
|---|---|
| 顧客（`DELETE /api/v1/customers/{id}`） | その顧客の、終わっていない予約。どのサロンの予約でも同じです（顧客台帳はプラットフォームで 1 つ） |
| スタッフ（`DELETE /api/v1/salons/{salonId}/staff/{id}`） | そのスタッフが担当スタッフである、終わっていない予約と、そのスタッフがどれかの施術明細を担当している、終わっていない予約 |
| サービス（`DELETE /api/v1/salons/{salonId}/services/{id}`） | そのサービスの施術明細を持つ、終わっていない予約 |
| サロン（`DELETE /api/v1/salons/{id}`） | そのサロンの、終わっていない予約 |

- 409 の `code` は `3003` で、`detail` は `The customer cannot be deleted: bookings that are not finished refer to it` の形です（`customer` のところが、`salon`、`service`、`staff member` になる）。件数や予約の ID は入れません。顧客の予約は、操作者に見えないサロンのものでありうるからです。該当する予約は、予約の一覧を `customerId`、`staffId`、`salonId` と `status` で絞り込んで探します
- 断ったときは、何も書きません。顧客のアカウントとプロフィールの紐づけも、そのままです
- それぞれの削除の、これまでの確認（権限、ID、対象があること）のあとで確かめます。権限のないユーザーには、予約があっても 403 です。スタッフの削除は、自分自身のスタッフ情報であること（409）を先に確かめ、サービスの削除は、パッケージに含まれていること（409）を先に確かめます
- 予約を片付けるのは、いまある操作です。完了、キャンセル、無断キャンセルの記録、予約の[削除](#削除)。担当スタッフは、[日時の変更](#日時の変更)でほかのスタッフに替えれば外れます（担当していた明細も付け替わる）。担当スタッフでないスタッフが担当する明細は、ほかのスタッフで明細を追加してから、そのスタッフの明細を削除すれば外れます（[施術明細の追加と削除](#施術明細の追加と削除)）。サービスも、その明細を削除すれば外れます
- 誰が削除できるか、削除が何を書くかは、変わりません（[顧客台帳](./customers.md#削除)、[スタッフ](./staff.md#削除)、[サービス](./service-menu.md#サービスの削除)）
- 作成と日時の変更、明細の追加は、削除されたものを新しく指す予約を断ります（400）。この規則と合わせて、終わっていない予約が、削除されたものを指すことはありません。この規則より前に削除された行を指す予約は、そのまま残ります（シードにはありません）
- 削除が書く `deletedAt` と `updatedAt` は、行をロックできたあとのデータベースの時計です（`clock_timestamp()`）。予約の書き込みを待った削除が、待つ前の時刻を書かないようにするためです

## 1 件の取得と一覧

- `services` は、明細を `sortOrder` の順に並べたものです
- 日時は UTC で、ミリ秒までの ISO 8601 形式です（`2026-11-20T01:00:00.000Z`）
- 一覧の並びは、開始日時（`startTime`）の早い順、同じ値の中では `id` の昇順です
- `limit` は 1〜100（既定は 20）。`cursor` は、前のページの最後の予約の ID です。操作者に見えない予約や、予約でない ID を指す `cursor` は 400 です（`cursor` の `not_found`）
- `meta.total` は、絞り込みに一致する予約の件数です
- サロンのユーザーが `salonId` を指定しなければ、所属サロンの予約だけを返します。ほかのサロンの `salonId` を指定すると 403 です
- 絞り込みは、すべて AND で結合します

| パラメーター | 一致する予約 |
|---|---|
| `salonId` | そのサロンの予約 |
| `customerId` | その顧客の予約 |
| `staffId` | そのスタッフが担当スタッフである予約と、どれかの明細を担当している予約 |
| `status` | ステータスが一致する |
| `bookingDateFrom` / `bookingDateTo` | 来店日がその日以降 / 以前（両端を含む）。`bookingDateFrom` が `bookingDateTo` より後なら 400（`bookingDateTo` の `custom`）。どちらも 1900-01-01 から 2999-12-31 まで |

- `customerId` や `staffId` に、存在しない ID やほかのサロンのスタッフの ID を指定しても、エラーにはしません。一致する予約がないだけです
- 保存されている行が API のモデルに合わないとき（マイグレーションより前の行など）は 500（データベースのエラー）です。読み出すときに検証します（`mappers/read/booking.mapper.ts`）
- 予約と明細は、1 つの問い合わせで読みます。完了の途中の予約を読んでも、「予約は完了で、明細は未完了」という組み合わせは返りません

## 空き枠

`/api/v1/salons/{salonId}/available-slots` の 2 つのオペレーション（`AvailableSlotCrud`）です。空き枠を保存するテーブルはありません。サロンの営業時間、スタッフの勤務スケジュール、すでにある予約から、リクエストのたびに算出します。

| オペレーション | ルート | 許可 |
|---|---|---|
| 一覧 | `GET /api/v1/salons/{salonId}/available-slots` | サインインしているすべてのユーザー |
| 確認 | `POST /api/v1/salons/{salonId}/available-slots/check` | `admin`、そのサロンの `owner` / `manager` / `staff` |

- 2 つは、答える問いが違います。**一覧は、顧客が予約できる枠を返します**。サロンが受け付けについて決めた設定（[受け付けの設定](#受け付けの設定)）を、すべて適用します。**確認は、台帳がその予約を受け付けるかどうかを答えます**。台帳が確かめるもの（[スタッフの占有](#スタッフの占有)）だけを確かめます
- 一覧は、枠があるかどうかだけを返し、どの予約のことも返しません。だから、サインインしていれば誰でも読めます。認証は要ります（コントラクトのとおり）
- 確認は、重なっている予約の ID を返します。だから、そのサロンの台帳に届く人だけが使えます（`business-logic/available-slot/_shared/authorization.ts` の `mayAskLedgerOf`。台帳と同じ `bookingReachOf` で決める）。顧客のアカウントと、ほかのサロンのユーザーには 403 を返します
- どちらも、何も書きません。枠を押さえることもしません。答えは、その時点のものです。顧客が枠に予約を入れるときに、同じ規則で、もう一度確かめます（[予約を入れる](#予約を入れる)）

### 枠の決め方

枠は、1 人のスタッフがサービスを始められる開始日時です。`staffId`、`startTime`、`endTime`（開始日時に施術時間を足した日時）を返します。

1. 施術時間は、クエリの `duration`（1〜1440 分）です。指定がなければ、サービスの `duration` です
2. サロンが開いている時間帯（[サロンの営業時間帯](#サロンの営業時間帯)）と、スタッフが勤務している時間帯（[スタッフの勤務時間帯](#スタッフの勤務時間帯)）の重なりを取ります
3. 重なりの時間帯ごとに、その始まりから 30 分おき（`SLOT_STEP_MINUTES`）に、開始日時を置きます。施術の全体が時間帯に収まるものだけです。10:00〜12:00 の時間帯と 60 分の施術なら、10:00、10:30、11:00 です。刻みは時間帯の始まりから数えるので、10:15 に始まる時間帯の枠は 10:15、10:45 と続きます
4. 現在（リクエストを処理する時点）より後に始まる枠だけを残します。過去の日付には、空の一覧を返します（エラーにはしません）
5. スタッフが占有されていない枠だけを残します。台帳と同じ規則です（`isOccupiedBeyondCapacity`。前後の空け時間と `maxConcurrentBookings` を含み、`cancelled` と `no_show` の予約は占有しません）。一覧が返した枠に、台帳で予約を入れると、そのあいだにほかの予約が入っていなければ、占有を理由に断られません

規則は `business-logic/available-slot/_shared/slots.ts` の `slotsOf` です。

### サロンの営業時間帯

- 営業日カレンダー（`opening_hours`）に、その日付の行があれば、その行だけで決まります。`openTime` から `closeTime` まで営業し、時刻のない行の日は終日休業です。`isHoliday` が true でも、時刻があれば、その時間は営業します（祝日の営業）
- 行がなければ、曜日ごとの営業時間（`businessHours`）の、その曜日のエントリーで決まります。`operatingSlots` から `breakSlots` を除いた時間です。`isClosed` なら休業です。`effectivePeriod` があれば、その期間の中だけ営業します
- その曜日のエントリーがないサロンと、`businessHours` が null のサロンは、その日は休業です
- カレンダーは、1 つのサロンの 1 つの日付に 1 行です。リクエストの検証に加えて、一意インデックス（`opening_hours_salon_date_unique`）が保証します（[DB の制約](#db-の制約)）
- 時刻は、サロンの `timezone` での、その日の時刻です（[来店日とサロンのタイムゾーン](#来店日とサロンのタイムゾーン)）
- 日付をまたぐ営業は表せません。終わりが始まり以前の時間帯（22:00〜02:00 など）は、サロンの作成と更新が 400 で断ります（スタッフの勤務スケジュールも同じ）。そのような値が保存されていても、空き枠は、時間がないものとして扱い、枠を作りません。0 時をまたぐ施術の枠はありません
- 夏時間のある地域では、時計を進める夜の、存在しない時刻を、その分だけ後の時点として読みます（02:00 が 03:00 になる夜の 02:30 は、03:30）。時計を戻す夜の、2 回ある時刻は、最初の時点です。00:00〜06:00 の営業は、進める夜には 5 時間、戻す夜には 7 時間になります

規則は `business-logic/available-slot/_shared/opening.ts` の `openRangesOf`、時刻から時点を決めるのは `_shared/salon-time.ts` の `momentAt` です。

### スタッフの勤務時間帯

- その日付に当てはまる勤務スケジュールの行で決まります（[スタッフ台帳](./staff.md#ある日付に適用される行)。その日付の行、なければ、その曜日の毎週の行）
- `startTime` から `endTime` まで勤務し、休憩（`breakStartTime`〜`breakEndTime`）を除きます
- 当てはまる行のない日と、休みの行（`isAvailable` が false）の日は、勤務しません。枠はありません

規則は `business-logic/available-slot/_shared/working.ts` の `workingRangesOf` です。

### 受け付けの設定

一覧は、次の場合に枠を返しません。エラーではなく、空の一覧（スタッフの設定は、そのスタッフの枠がないだけ）です。

| 設定 | 枠を返さない場合 |
|---|---|
| サロンの `isActive` | false |
| サービスの `isActive`、`serviceStatus`、`allowOnlineBooking` | `isActive` が false、`serviceStatus` が `active` 以外、`allowOnlineBooking` が false |
| サービスの `availability` | `weekdays_only` で土曜日・日曜日、`weekends_only` で月曜日〜金曜日（サロンのタイムゾーンでの曜日）。`always`、`by_appointment_only`、`seasonal` は、どの日も同じに扱う |
| サービスの `bookingRequirements` | `advance_booking_required` があり、日付が、サロンのタイムゾーンでの今日。ほかの値は、サーバーでは確かめられないので、枠に影響しない |
| サービスの `maxBookingsPerDay` | その日（サロンのタイムゾーンでの日付）に始まる、そのサービスの明細の数が、その値に達している。`cancelled` と `no_show` の予約の明細は数えない。担当スタッフが誰でも（未定でも）数える |
| スタッフの `isActive`、`canReceiveBookings` | どちらかが false |
| スタッフの `level` | サービスの `requiredStaffLevel` に満たない（`junior` < `stylist` < `senior` < `expert` < `director`） |

- `by_appointment_only` は、空き枠からの予約が事前の予約なので、ほかの日と同じです。`seasonal` は、サロンが季節ごとに `serviceStatus` を切り替えます
- サービスの `requiresConsultation`、顧客の設定と好み設定は使いません。どのスタッフがどのサービスを担当できるかの表もありません。サロンのスタッフは、ランクが足りれば、どのサービスも担当できるものとして扱います
- これらの設定は、台帳に入れる予約を止めません（[サロンが台帳に入れる予約は、サロンの判断](#サロンが台帳に入れる予約はサロンの判断)）。`maxBookingsPerDay` に達した日にも、サロンは台帳から予約を入れられます

規則は `business-logic/available-slot/_shared/acceptance.ts` です。

### 一覧

- クエリは、`serviceId`（必須）、`date`（必須。`YYYY-MM-DD`。サロンのタイムゾーンでの日付。1900-01-01 から 2999-12-31 まで）、`staffId`（指定すると、そのスタッフの枠だけ）、`duration`、`limit`（1〜100。既定は 20）、`cursor` です。ほかのパラメーターは 400 です
- 並びは、`startTime` の早い順、同じ日時の中では `staffId` の昇順です
- `meta.total` は、その日の枠の数です（`cursor` によらない）
- 枠には ID がないので、`cursor` は、ページの最後の枠そのもの（`<startTime>_<staffId>`）です。次のページは、その枠より後の枠から返します。カーソルの枠が、そのあいだに埋まっていても、続きを返します。この形でない `cursor` は 400 です（`cursor` の `custom`）
- ページは、次にだけ進みます。`meta.prevCursor` と、`links` の `prev`、`last` は null です
- 確認の順序は、認証（401）、パスの `salonId`（400）、クエリ（400）、サロンがあるか（404）、`staffId` と `serviceId` がそのサロンのものか（400。`not_found`。削除済みのものを含み、両方をまとめて報告する）、サロンのタイムゾーン（409）です
- サロンの `timezone` が名前として読めないとき（以前に保存された値）は 409 です。時刻を時点に直せないからです。以前に保存されたオフセット（`+09:00`）は読めます
- 保存されている `businessHours` が API のモデルに合わないときは 500（データベースのエラー）です
- 読み出しは、1 つのトランザクション（`REPEATABLE READ`、読み取り専用）で行います。サロン、スタッフ、スケジュール、予約を、同じ時点のものとして読みます。ロックは取らず、待ちません

### 確認

- 本文は、`staffId`、`serviceId`、`startTime`（UTC の分単位。UTC の日付で 1900-01-01 から 2999-12-31 まで）です。3 つとも必須で、ほかのプロパティは 400 です
- 希望する時間は、`startTime` から、サービスの `duration` のあいだです
- `isAvailable` は、その時間に、スタッフが占有されていないことです。台帳への作成、日時の変更、明細の追加が、スタッフの占有を理由に 409 にならないことを表します
- `conflicts` は、希望する時間に明細が重なっている予約の ID です。希望する時間にも、明細にも、スタッフの前後の空け時間を加えて比べます。早く始まる明細の予約から並べ、1 つの予約は 1 回だけ返します
- 同時に複数の予約を受けられるスタッフ（`maxConcurrentBookings` が 2 以上）では、`conflicts` があっても、`isAvailable` が true のことがあります
- **確かめるのは、占有だけです**。営業時間、勤務スケジュール、受け付けの設定、過去の日時かどうかは確かめません。台帳が確かめないものは、確かめません
- 確認の順序は、認証（401）、パスの `salonId`（400）、権限（403。本文を読む前に決める。存在しないサロンでも 403）、本文（400）、サロンがあるか（404）、`staffId` と `serviceId` がそのサロンのものか（400。`not_found`）です
- 答えのあとで、ほかの予約が入ることがあります。そのあとの作成は 409 になりえます
- `links` は、`self`（確認）と `list`（そのサロンの空き枠の一覧）です

## 顧客が自分で入れる予約

`/api/v1/customers/me/bookings` の 5 つのオペレーション（`CustomerBookings`）です。顧客が、自分のアカウントで、空き枠に予約を入れ、自分の予約を読み、日時を変え、キャンセルします。ルートは、プロフィールと好み設定（[顧客台帳](./customers.md#顧客本人のプロフィール)）と同じく、`/api/v1/customers/me` の下にあります。

| オペレーション | ルート | 成功 |
|---|---|---|
| 一覧 | `GET /api/v1/customers/me/bookings` | 200。自分の予約の一覧 |
| 作成 | `POST /api/v1/customers/me/bookings` | 201。入れた予約。`Location` ヘッダーに予約の URL |
| 1 件の取得 | `GET /api/v1/customers/me/bookings/{id}` | 200。自分の予約 |
| キャンセル | `POST /api/v1/customers/me/bookings/{id}/cancel` | 200。キャンセルした予約 |
| 日時の変更 | `POST /api/v1/customers/me/bookings/{id}/reschedule` | 200。変更した予約 |

- 使えるのは、ロール `customer` のユーザーだけです。`admin` とサロンのユーザー、ロールに必要なレコードを持たないユーザー（範囲 `none`）には 403 を返します。これらのユーザーは、台帳を使います。権限は、パスの ID、クエリ、本文のどれよりも先に確かめます（`business-logic/customer-booking/_shared/access.ts` の `ownBookingsOf`）
- プロフィール（自分の顧客レコード）をまだ作っていないアカウントと、顧客レコードが削除されたアカウントには 404 を返します（プロフィール、好み設定と同じ）
- 届くのは、自分の予約だけです。**ほかの顧客の予約は、存在しない予約と区別しません**。取得、キャンセル、日時の変更は 404、一覧には出ず、カーソルに指定すると 400 です
- **サロンが台帳に入れた自分の予約も、自分の予約です**（電話で入れた予約など）。読めて、同じ規則でキャンセルと日時の変更ができます。どのサロンの、どのステータスの予約も対象です
- 日時と担当スタッフは、空き枠にだけ変えられます（[顧客による日時の変更](#顧客による日時の変更)）。サービスは変えられません。キャンセルして、入れ直します（キャンセル回数が 1 つ増えます）
- レスポンスの `links` は、`self` と `list`（`/api/v1/customers/me/bookings`）です

### 顧客に見せる項目

レスポンス（`CustomerBookingResponse`）は、予約のうち、顧客に見せる項目だけです。プロパティ名と null 許可は、台帳の `BookingResponse` と同じです（DB のカラムと同じ）。

| | 項目 |
|---|---|
| 予約 | `id`、`bookingNumber`、`salonId`、`staffId`、`bookingDate`、`startTime`、`endTime`、`duration`、`status`、`subtotal`、`discountAmount`、`taxAmount`、`totalAmount`、`depositAmount`、`pointsUsed`、`pointsEarned`、`customerRequest`、`cancelledAt`、`cancellationFee`、`completedAt`、`services`、`createdAt`、`updatedAt` |
| 明細（`CustomerBookingServiceResponse`） | `id`、`serviceId`、`staffId`、`startTime`、`endTime`、`duration`、`price`、`discountAmount`、`finalPrice`、`taxIncluded`、`sortOrder` |

出さないものは、次のとおりです。

- サロン内のメモ: `internalNotes`、明細の `notes`
- サロンの記録: `source`、`reminderSent`、`reminderSentAt`、`actualStartTime`、`actualEndTime`、明細の `isCompleted`・`completedAt`
- 誰がキャンセルしたかと、その理由: `cancelledBy`、`cancellationReason`。スタッフが書いた理由は、顧客に向けた文とは限りません。顧客が自分で書いた理由も、返しません
- `customerId`: 自分のものなので、出しません

読み出しは、台帳と同じマッパーで検証してから、見せる項目を 1 つずつ取り出します（`mappers/read/customer-booking.mapper.ts`）。台帳のレスポンスに項目を加えても、顧客のレスポンスには出ません。

### 予約を入れる

本文（`CustomerBookingCreateRequest`）は、全項目が必須です。ほかのプロパティは 400 です（`unrecognized_keys`）。`customerId` も書けません。予約は、アカウントの顧客のものです。

| 項目 | 型 | 規則 |
|---|---|---|
| `salonId` | `SalonId` | 削除されていないサロン |
| `serviceId` | `ServiceId` | そのサロンの、削除されていないサービス |
| `staffId` | `StaffId` | そのサロンの、削除されていないスタッフ |
| `startTime` | `utcDateTime` | UTC（`Z`）で、分単位。UTC の日付で 1900-01-01 から 2999-12-31 まで |
| `customerRequest` | `string \| null` | 空白だけでない |

- **入れられるのは、空き枠の一覧が、その時点で返す枠だけです**。`staffId` と `startTime` が、そのサービスの、その日（サロンのタイムゾーンでの `startTime` の日付）の空き枠でなければ 409 です。サロンの営業時間、スタッフの勤務、[受け付けの設定](#受け付けの設定)、いまより後であること、スタッフの占有を、空き枠の一覧と同じ 1 つの関数（`slotsOf`）で確かめます。施術時間は、サービスの `duration` です（一覧の `duration` パラメーターにあたるものは、ありません）
- 「いま」は、空き枠の一覧と同じく、アプリケーションの時計です
- **1 つの予約に、サービスは 1 つです**。明細は 1 件で、担当は `staffId` のスタッフです。空き枠の一覧が、サービスを 1 つしか受け取らないからです。複数のメニューを 1 回で受けるには、サロンがパッケージのサービス（`isPackage`）を用意します。入れたあとで、サロンは台帳から明細を足せます
- システムが決める値は、台帳の作成と同じです（[システムが決める値](#システムが決める値)。金額と時間はサービスの写し、`status` は `pending`、予約番号、`bookingDate`、消費税）。`depositAmount` と `internalNotes`、明細の `notes` は null、`source` は `online` です。ステータスの履歴の `changedBy` は、顧客のユーザー ID です。書く行は、サロンが同じ内容を台帳に入れたときと同じです（`planCustomerBooking` が、台帳の `planBooking` で作る）
- 入れた予約は `pending` です。サロンが、台帳で確定します。自動で確定するかどうかの、サロンの設定はありません
- 枠でない理由（営業時間の外か、スタッフが占有されているか、など）は、区別して返しません。画面は、空き枠の一覧を読み直します

#### 顧客の状態

顧客レコードの `isActive` が false、または `customerStatus` が `inactive` か `blacklisted` の顧客は、自分では予約を入れられません（409）。`active` と `vip` は入れられます（`business-logic/available-slot/_shared/acceptance.ts` の `booksOnline`）。

- `detail` は、理由を書きません。状態は、サロンが顧客について記録したもので、本人には見せていない項目です（[顧客台帳](./customers.md#本人に見せる項目本人が書ける項目)）
- その顧客の予約を、サロンが台帳に入れることは、妨げません（[サロンが台帳に入れる予約は、サロンの判断](#サロンが台帳に入れる予約はサロンの判断)）
- 自分の予約を読むことと、キャンセルすることは、どの状態の顧客にもできます。日時の変更は、予約を入れるのと同じく、できません（409）
- 空き枠の一覧は、顧客の状態を見ません。誰が読んでも、同じ枠を返します

#### 同じ時間の予約

自分の、ほかの予約と時間が重なる予約は、入れられません（409）。1 人の顧客は、同時に 2 か所にいられないからです。

- 比べるのは、予約の `startTime` から `endTime` までです。終わりは含みません（10:00〜11:00 の予約がある顧客は、11:00 からの予約を入れられる）。スタッフの前後の空け時間は、顧客の時間には加えません
- `cancelled` と `no_show` の予約は、比べません。ほかのステータスの予約は、どのサロンの予約でも、サロンが台帳に入れた予約でも、比べます
- 二重に送信したリクエストが、同時に複数を受けるスタッフ（`maxConcurrentBookings` が 2 以上）に 2 件入ることも、この規則で防ぎます
- 顧客による日時の変更も、移る先を、同じ規則で確かめます。動かす予約そのものは、比べません
- サロンが台帳に入れる予約と、台帳での日時の変更は、顧客のほかの予約を確かめません（これまでどおり）

#### 予約を入れるときの確認の順序

1. 認証（401）
2. ロール `customer` であること（403）
3. プロフィールがあること（404）
4. 本文（400）
5. 顧客レコードが削除されていないこと（404。認証のあとで削除された場合）
6. `salonId`、`serviceId`、`staffId`（400。`not_found`。サロンがなければ `salonId` だけを、あれば、サービスとスタッフをまとめて報告する）
7. サロンのタイムゾーン（409。台帳、空き枠と同じ）
8. 顧客の状態（409）
9. 空き枠であること（409）
10. 自分のほかの予約と重ならないこと（409）

- 読めない本文（JSON でない、JSON の `null`）は、ほかのルートと同じく、認証より前に 400 です
- 保存されている `businessHours` が API のモデルに合わないサロンは 500 です（空き枠の一覧と同じ）
- 5 からあとは、1 つのトランザクションの中で、ロックを取ったあとに確かめます（[同時に届いたリクエスト](#同時に届いたリクエスト)）

### 顧客によるキャンセル

本文は、台帳のキャンセルと同じ `BookingCancelRequest` です（`cancellationReason`。`string | null` で、空白だけでない）。

- キャンセルできるのは、`draft`、`pending`、`confirmed` の予約（台帳のキャンセルと同じ）で、**開始日時より前**であることです。開始日時になった予約は 409 です。来店しなかった予約は、サロンが、キャンセルか無断キャンセルとして記録します
- 日時は、データベースの時計で決めます（ほかのステータスの操作と同じ。予約の行をロックできた時点の時刻）
- 締め切り（何時間前まで）と、キャンセル料は、定義していません。`cancellationFee` は 0 です（台帳と同じ）
- 書く値は、台帳のキャンセルと同じです（[各操作が書く値](#各操作が書く値)。`cancelledAt`、`cancelledBy` は顧客のユーザー ID、`cancellationReason`、履歴の 1 行、顧客のキャンセル回数の数え直し）。キャンセルした予約は、スタッフを占有しないので、その時間は空き枠に戻ります
- 確認の順序は、認証（401）、ロール `customer`（403）、プロフィール（404）、ID の形式（400）、本文（400）、予約があるか（404。ほかの顧客の予約も同じ）、ステータス（409）、開始日時より前であること（409）です
- 規則は、ステータスの操作の 1 つです（`business-logic/booking/_shared/status.ts` の `cancelAsCustomer`）。台帳のキャンセルとの違いは、開始日時を確かめることだけです

### 顧客による日時の変更

`POST /api/v1/customers/me/bookings/{id}/reschedule` は、自分の予約を、別の空き枠に移します。本文は、台帳の日時の変更と同じ `BookingRescheduleRequest` です（`startTime` と `staffId`。どちらも必須で、担当を変えないときは、いまの担当スタッフを書く。ほかの項目は 400）。

- 変えられるのは、`draft`、`pending`、`confirmed` の予約（台帳の日時の変更と同じ）で、**開始日時より前**であることです（キャンセルと同じ）。開始日時になった予約は 409 です
- **変えられるのは、枠で表せる予約だけです**。施術明細が 1 件で、その担当が、予約の担当スタッフである予約です。顧客が自分で入れた予約は、サロンが明細を足していなければ、この形です。サロンが明細を足した予約と、明細の担当がほかのスタッフか、決まっていない予約は 409 です。サロンに連絡して、台帳で変えてもらいます
- **移る先は、空き枠だけです**。`staffId` と `startTime` が、予約のサービス（明細のサービス）の、その日（サロンのタイムゾーンでの `startTime` の日付）の空き枠でなければ 409 です。予約を入れるときと同じ関数で確かめます（`business-logic/customer-booking/_shared/plan.ts` の `refusalOfSlot`。枠は `slotsOf` が決める）。違いは 2 つです
  - 施術時間は、予約の明細の長さです（予約を入れたときのサービスの写し）。そのあとでサービスの `duration` が変わっていても、予約の長さは変わりません
  - **動かす予約そのものは、ないものとして確かめます**。自分の明細は、スタッフを占有せず、サービスの 1 日の上限（`maxBookingsPerDay`）にも数えません。10:00 からの 1 時間の予約を、10:30 からに移せます
- [受け付けの設定](#受け付けの設定) は、変更の時点のものです。予約を入れたあとで、サービスがオンラインの受け付けを止めた、スタッフが予約を受けなくなった、などの場合、顧客は、その予約を自分では移せません（409。サロンに連絡する）。キャンセルは、できます
- [顧客の状態](#顧客の状態) と [同じ時間の予約](#同じ時間の予約) は、予約を入れるときと同じです。状態が、予約を入れられないものなら 409（理由は書かない）、移る先が、自分のほかの予約と重なれば 409 です
- 「いま」は、アプリケーションの時計です（予約を入れるときと同じ）。開始日時より前かどうかと、移る先がいまより後かどうかを、同じ 1 つの時点で決めます。キャンセルは、データベースの時計で決めます
- 書くのは、台帳の日時の変更と同じ値です（[日時の変更](#日時の変更)。予約の `staffId`、`bookingDate`、`startTime`、`endTime` と、明細の `staffId`、`startTime`、`endTime`）。`duration`、金額、明細のサービスと料金は変わりません。顧客の回数も数え直しません
- **確定済みの予約は、確定待ちに戻ります**。`confirmed` の予約は `pending` になり、ステータスの履歴に 1 行書きます（`fromStatus` が `confirmed`、`toStatus` が `pending`、`changedBy` が顧客のユーザー ID、`reason` は null）。サロンが確定したのは、変更前の日時と担当だからです。サロンは、台帳の一覧（`status=pending`）で見つけて、確定し直します。`draft` と `pending` の予約は、ステータスが変わらず、履歴も書きません
- **担当スタッフも開始日時も、いまと同じリクエストは、何も変えません**。200 で、いまの予約を返します（`confirmed` の予約は `confirmed` のままで、`updatedAt` も変わらない）。送り直したリクエストが、サロンが確定し直した予約を、もう一度、確定待ちに戻すことはありません。台帳の日時の変更は、同じ日時でも `updatedAt` を書きます
- 空き枠でない理由は、予約を入れるときと同じく、区別して返しません。画面は、空き枠の一覧を読み直します
- 規則は `business-logic/customer-booking/_shared/move.ts` です。`moveCustomerBooking` が、動かせる予約かを決めて（台帳の `moveBooking` で動かす）、`planCustomerMove` が、移る先を確かめて、書く行を決めます（台帳の `planReschedule` で作る）

#### 移せる先を一覧で読む

移せる先を画面に出すには、空き枠の一覧を、予約のサービスと、予約の施術時間で読みます（`GET /api/v1/salons/{salonId}/available-slots` の `serviceId`、`date`、`duration`）。

- 一覧が返す枠には、どれにも移せます（顧客の状態と、自分のほかの予約が許せば）
- 一覧は、動かす予約そのものも、占有として数えます。その予約と重なる時間の、同じスタッフの枠は、一覧には出ませんが、指定すれば移せます。その予約を除いて数える一覧は、ありません

#### 日時を変えるときの確認の順序

1. 認証（401）
2. ロール `customer` であること（403）
3. プロフィールがあること（404）
4. ID の形式（400）
5. 本文（400）
6. 予約があるか（404。ほかの顧客の予約も同じ）
7. ステータス（409）
8. 開始日時より前であること（409）
9. 枠で表せる予約であること（409）
10. 担当スタッフも開始日時も同じなら、ここで 200（何も書かない）
11. `staffId` が、予約のサロンの、削除されていないスタッフであること（400。`not_found`）
12. サロンのタイムゾーン（409）
13. 顧客の状態（409）
14. 空き枠であること（409）
15. 自分のほかの予約と重ならないこと（409）

- 6 からあとは、1 つのトランザクションの中で、予約の行をロックしたあとに確かめます（[同時に届いたリクエスト](#同時に届いたリクエスト)）
- 終わっていない予約が参照するサロン、顧客、サービス、スタッフは、削除できません（[予約が参照するものの削除](#予約が参照するものの削除)）。それでも、顧客レコードが削除されていれば 404、予約のサロンかサービスが削除されていれば、空き枠でない（409）として扱います。どちらも、11 より前に確かめます
- 保存されている `businessHours` が API のモデルに合わないサロンは 500 です（空き枠の一覧と同じ）

### 自分の予約の一覧と取得

- クエリ（`CustomerBookingSearchRequest`）は、`status`、`bookingDateFrom`、`bookingDateTo`、`limit`（1〜100。既定は 20）、`cursor` です。規則は、台帳の一覧の同じパラメーターと同じです（[1 件の取得と一覧](#1-件の取得と一覧)）。台帳の `salonId`、`customerId`、`staffId` を含めて、ほかのパラメーターは 400 です
- 並びは、台帳と同じです（開始日時の早い順、同じ値の中では `id` の昇順）
- `meta.total` は、絞り込みに一致する、自分の予約の件数です
- `cursor` が自分の予約を指していなければ 400 です（`cursor` の `not_found`）

作成は 1 つのトランザクションです（`infrastructure` の `BookingRepository.create`）。

1. サロン、顧客、サービスの行を、この順に共有ロック（`FOR SHARE`）します。確認した行が、書き終わるまで削除されず、料金も変わらないようにするためです。共有ロックどうしは待たせないので、台帳に入れる、同じ顧客や同じサービスの予約は並行して進みます
2. リクエストが挙げたスタッフ（担当スタッフと、明細のスタッフ）の行を、1 つの問い合わせで、ID の順に排他ロック（`FOR UPDATE`）します。同じスタッフへの予約は 1 件ずつ処理されるので、同時に届いた 2 件が、どちらも「空いている」と判断して両方書かれることはありません。どのリクエストも同じ順にロックするので、デッドロックになりません
3. 占有を確かめて、予約、明細、履歴を書きます

このトランザクションは、分離レベルを `READ COMMITTED` と明示しています。ロックを待ったあとの問い合わせが、待っている間に書かれた予約を見るためです。トランザクション全体で 1 つのスナップショットを使う分離レベル（`REPEATABLE READ`）では、待っていた相手の予約が見えず、両方が書かれます。

顧客が自分で入れる予約も 1 つのトランザクションです（`BookingRepository.book`。分離レベルは `READ COMMITTED`）。

1. サロンの行を共有ロック、顧客の行を排他ロックします。どちらかがなければ、ここで終わります
2. サービスの行を排他ロック、スタッフの行を排他ロックします（リクエストのサロンの、削除されていない行だけ）
3. 枠を決めるのに要るものを読みます。スタッフの勤務スケジュール、サロンの営業日カレンダー、スタッフの明細、そのサービスの明細の開始日時、顧客のほかの予約です。**どれも、ロックを取ったあとの問い合わせで読みます**。待っている間に入った予約と、変わった設定を見ます
4. `planCustomerBooking` が、予約を入れられるかを決めて、書く行を作ります。入れられなければ、何も書かずに終わります
5. 予約、明細、履歴を書きます（台帳の作成と同じ書き込み）

- ロックの順は、台帳の作成と同じ（サロン、顧客、サービス、スタッフ）で、顧客とサービスは、台帳より強いロックです
- スタッフの排他ロックで、同じスタッフへの予約は、台帳からのものも含めて、1 件ずつ処理されます
- サービスの排他ロックで、同じサービスへの顧客の予約は 1 件ずつ処理されます。`maxBookingsPerDay` の残りが 1 件の日に、スタッフが別々の予約が同時に届いても、1 件だけが書かれます。台帳の作成と明細の追加は、サービスを共有ロックするので、顧客の予約を書いている間は待ちます（台帳は `maxBookingsPerDay` を確かめないので、待つだけです）
- 顧客の排他ロックで、同じ顧客の予約は 1 件ずつ処理されます。同じ時間の予約が同時に届いても、1 件だけが書かれます
- サロンのタイムゾーンは、ロックのあとで分かります。だから、読む範囲は、`startTime` がどのタイムゾーンでも入る広さにします（UTC での日付と、その前後の日付。`candidateDatesOf`、`candidateTimeOf`）。その中から、サロンのタイムゾーンでの日付のものを、`planCustomerBooking` が選びます

顧客による日時の変更も 1 つのトランザクションです（`BookingRepository.rebook`。分離レベルは `READ COMMITTED`）。

1. 予約の行を排他ロックして、ステータス、担当スタッフ、日時を読み、明細を読みます（台帳の日時の変更と同じ。範囲は、その顧客の予約）
2. `moveCustomerBooking` が、動かせる予約かを決めます。動かせなければ、何も書かずに終わります。担当スタッフも開始日時も同じなら、いまの予約を読んで返します
3. 顧客が予約を入れるときと同じ順に、同じロックを取り、同じものを読みます（サロンは予約のサロン、サービスは明細のサービス）。**動かす予約の明細は、スタッフの明細にも、そのサービスの明細にも含めず、動かす予約は、顧客のほかの予約に含めません**
4. `planCustomerMove` が、移せるかを決めて、書く行を作ります。移せなければ、何も書かずに終わります
5. 予約と明細を書き、確定済みだった予約なら、履歴を 1 行書きます。`updatedAt` と、履歴の `createdAt` は、書く時点の `clock_timestamp()` です

- 予約の排他ロックで、同じ予約への変更、キャンセル、サロンの操作は 1 件ずつ処理されます。待っていた変更は、先の操作のあとの予約を読みます（キャンセルされていれば 409、同じ先に移っていれば、何も書かない）
- スタッフ、サービス、顧客の排他ロックの役目は、予約を入れるときと同じです。同じ枠への変更と作成、同じ顧客の 2 件の予約を同じ時間に移す変更は、1 件ずつ処理されます

ステータスの操作も 1 つのトランザクションです（`BookingRepository.changeStatus`。分離レベルは `READ COMMITTED`）。顧客によるキャンセルも、範囲が顧客の予約であることのほかは、同じトランザクションです。

1. 予約の行を排他ロック（`FOR UPDATE`）して、ステータスと日時を読み、ロックできた時点のデータベースの時計を読みます（ロックする副問い合わせが返した行に対して、外側の問い合わせが `clock_timestamp()` を読む。1 つの問い合わせ）。同じ予約への操作は 1 件ずつ処理され、待っていた操作は、先の操作が書いたステータスを読み、先の操作より後の時刻を書きます
2. `planStatusChange` が、操作できるかを決めます。できなければ、何も書かずに終わります
3. 予約、明細（完了のとき）、履歴を書きます。`updatedAt` と、履歴の `createdAt` は、書く時点の `clock_timestamp()` です
4. 完了、キャンセル、無断キャンセルの記録では、顧客の行を排他ロックしてから、顧客の予約を数え直します。ロックがないと、同じ顧客の 2 つの予約への操作が、互いの結果を見ずに数え、あとから書いた方が、もう片方を数えない値を残します

ロックの順は、いつも予約、顧客の順です。スタッフの行はロックしません（キャンセルで占有が減っても、待っている作成はない）。

更新、日時の変更、削除も、それぞれ 1 つのトランザクションです（`BookingRepository.update`、`reschedule`、`delete`。分離レベルは `READ COMMITTED`）。**予約やその明細を書くものは、どれも、最初に予約の行を排他ロックします**。同じ予約への変更は 1 件ずつ処理され、待っていた変更は、先の変更のあとの予約を読みます。書く時刻（`updatedAt`）は、ロックできたあとの `clock_timestamp()` です。更新は、予約をロックして、指定された項目を書くだけです。

日時の変更:

1. 予約の行を排他ロックして、ステータス、担当スタッフ、日時を読み、明細を読みます
2. `moveBooking` が、動かせるステータスかを決めます。動かせなければ、何も書かずに終わります
3. サロンの行を共有ロックして、タイムゾーンを読みます。変更後の予約に関わるスタッフ（新しい担当スタッフと、明細のスタッフ）の行を、1 つの問い合わせで、ID の順に排他ロックします（作成と同じ）
4. `planReschedule` が、担当スタッフとタイムゾーンを確かめて、書く行を決めます
5. 占有を、この予約の明細を除いて確かめ、予約と明細を書きます

削除:

1. 予約の行を排他ロックします。その予約の会計を書いている途中の売上の作成と、売上をその予約に変えている途中の更新は、予約の行を排他ロックしています（[売上台帳](./sales.md#同時に届いたリクエスト)）。予約を参照する行をほかの方法で書くトランザクションも、外部キーの確認のために予約の行をロックします。削除は、どちらも待ちます
2. 予約を参照する売上、施術記録、レビューを探します。あれば、何も消さずに終わります
3. 予約を削除します（明細と履歴は外部キーで消える）。数えられていたステータスなら、顧客の行を排他ロックして、数え直します

施術明細の追加と削除も、それぞれ 1 つのトランザクションです（`BookingRepository.addService`、`removeService`。分離レベルは `READ COMMITTED`）。

明細の追加:

1. 予約の行を排他ロックして、ステータスを読み、明細を読みます。サロンの行を共有ロックして、タイムゾーンと税率を読みます。予約を算出している間に、どちらも変わりません
2. 本文のサービスの行を共有ロック、スタッフの行を排他ロックして読みます（作成と同じ。予約のサロンの、削除されていない行だけ）。サービスは、明細を書き終わるまで削除されず、料金も変わりません。同じスタッフへの書き込みは、1 件ずつ処理されます
3. `planServiceAddition` が、追加できるかを決めて、明細の行と、算出し直した予約の値を作ります。追加できなければ、何も書かずに終わります
4. 占有を、この予約の明細を除いて確かめ、明細を書き、予約を書きます。明細の `createdAt`・`updatedAt` と、予約の `updatedAt` は、書く時点の `clock_timestamp()` です。明細の 2 つは、時計を 1 回読んだ、同じ時刻です

明細の削除:

1. 予約の行を排他ロックして、ステータスと明細を読み、サロンの行を共有ロックします
2. `planServiceRemoval` が、削除できるかを決めて、算出し直した予約の値を作ります。削除できなければ、何も書かずに終わります
3. 明細を削除して、予約を書きます。スタッフの行はロックしません（占有が減っても、待っている書き込みはない）

ロックの順は、作成（台帳も、顧客が自分で入れる予約も）がサロン、顧客、サービス、スタッフ、台帳での日時の変更が予約、サロン、スタッフ、顧客による日時の変更が予約、サロン、顧客、サービス、スタッフ、明細の追加が予約、サロン、サービス、スタッフ、明細の削除が予約、サロン、ステータスの操作と削除が予約、顧客です。売上の作成（[売上台帳](./sales.md)）は、予約、サロン、顧客、スタッフの順です。売上の更新は、売上、予約、顧客、スタッフの順で、取り消しは、売上だけです。支払いの記録は、売上、支払い方法の順で、返金は、売上だけです（[支払い](./payments.md#支払いの記録と返金)）。売上の行は、この 4 つだけがロックし、予約、顧客、スタッフの行を先にロックする操作は、売上の行をロックしません。予約の作成は、すでにある予約の行をロックしません。どの 2 つを組み合わせても、同じ行を逆の順にロックすることはないので、デッドロックになりません。

顧客、スタッフ、サービス、サロンの削除も、それぞれ 1 つのトランザクションです（`CustomerRepository`、`StaffRepository`、`ServiceRepository`、`SalonRepository` の `delete`。分離レベルは `READ COMMITTED`）。

1. 削除する行を排他ロック（`FOR UPDATE`）します。その行を指す予約を書いている途中の作成と日時の変更、明細の追加は、その行をロックしているので（サロン、顧客、サービスは共有、スタッフは排他）、削除はそれを待ちます
2. 次の文で、その行を指す、終わっていない予約を探します（`repositories/unfinished-bookings.ts`）。あれば、何も書かずに終わります。ロックと同じ文で探すと、ロックを待つ前のスナップショットで探すことになり、待っている間に書かれた予約が見えません
3. 削除の印を付けます

削除は、予約の行をロックしません（読むだけです）。予約を書くものは、予約、そのあとで予約が参照する行、の順にロックするので、削除が予約の行をロックすると、逆の順になるからです。削除がロックするのは、削除する行だけ（顧客の削除は、そのあとでアカウントの行）なので、予約のどの書き込みとも、デッドロックになりません。あとから届いた作成と日時の変更、明細の追加は、削除が終わるのを待ち、削除された行を見て 400 を返します。終わった予約が、終わっていない予約に戻ることはなく（[ステータスの操作](#ステータスの操作)）、予約の参照を増やすのは、作成と日時の変更、明細の追加だけです。

取得と一覧は、ロックを待ちません。空き枠の一覧と確認も、ロックを取らず、待ちません。

## DB の制約

マイグレーション `202611160200_bookings_rules.sql` で、次のようにしました。

- 既定値をなくした（NULL 可のまま）: `bookings.depositAmount`、`pointsUsed`、`pointsEarned`、`cancellationFee`（以前は 0）、`booking_services.selectedOptions`（以前は `[]`。のちに `202611181200_unused_tables_and_columns.sql` で削除）。設定していない値は NULL です
- `bookings` の CHECK 制約: 終了が開始より後（`bookings_end_after_start`）、`duration` が開始から終了までの分数（`bookings_duration_is_the_span`）、金額は 0 以上（`bookings_amounts_not_negative`）、`discountAmount` は `subtotal` 以下（`bookings_discount_within_subtotal`）、`totalAmount` = `subtotal` − `discountAmount` + `taxAmount`（`bookings_total_is_the_sum`）
- `booking_services` の CHECK 制約: 終了が開始より後（`booking_services_end_after_start`）、`duration` が開始から終了までの分数（`booking_services_duration_is_the_span`）、`discountAmount` は 0 以上で `price` 以下（`booking_services_discount_within_price`。`price` が 0 以上であることも、これで決まる）、`finalPrice` = `price` − `discountAmount`（`booking_services_final_price_is_the_difference`）、`isCompleted` と `completedAt` が合っている（`booking_services_completed_has_time`）、`sortOrder` は 0 以上（`booking_services_sort_order_not_negative`）
- 一意制約: 1 つの予約の中で `sortOrder` は重ならない（`booking_services_order_unique`）
- インデックス: `booking_services` の `(staffId, startTime)`（`idx_booking_services_staff_start`。スタッフの占有を調べる）、`bookings` の `(salonId, startTime, id)`（`idx_bookings_salon_start`。サロンの予約を一覧の順に読む）。それぞれ、先頭のカラムだけのインデックスを置き換えた

以前の行は、ほかのカラムから決まる値をマイグレーションが直します（予約と明細の `duration`、予約の `totalAmount`、明細の `finalPrice`、明細の `sortOrder` は元の順のまま 0 から振り直す）。決められないもの（終了が開始より後でない、金額が負、完了しているのに完了日時がない、など）があると、マイグレーションは失敗します。行を直してから、やり直します。

マイグレーション `202611160300_booking_status_rules.sql` で、ステータスと、ステータスに伴う値の関係を制約にしました。

- `bookings` の CHECK 制約: `cancelled` の予約にだけ、キャンセル日時がある（`bookings_cancelled_has_time`。`cancelled` なら必ずある）、キャンセルした利用者・理由・キャンセル料は `cancelled` の予約にだけある（`bookings_cancellation_only_when_cancelled`）、`completed` の予約にだけ、完了日時がある（`bookings_completed_has_time`。`completed` なら必ずある）、`in_progress` の予約には実際の開始日時がある（`bookings_in_progress_has_start`）、実際の終了は実際の開始より後（`bookings_actual_end_after_start`）
- `customers` の CHECK 制約: 来店回数が 0 のときにだけ、初回と最終の来店日が null で、初回は最終より後でない（`customers_visit_days_go_with_visits`）、3 つの回数は 0 以上（`customers_counts_not_negative`）
- 以前の行: キャンセルしていない予約のキャンセル料 0 は、以前の既定値なので、NULL にします。顧客の 5 つの値は、予約から数え直します（これまでは、シードだけが、予約と合わない値を書いていました）
- ほかの違反（キャンセル日時のない `cancelled` の予約、完了日時のない `completed` の予約など）は、どちらが正しいかを決められないので、直しません。マイグレーションは失敗し、何も変えません

マイグレーション `202611160400_booking_services_tax_included.sql` で、`booking_services` に `taxIncluded`（`boolean NOT NULL`、既定値なし）を加えました。明細の料金が消費税を含むかどうかの、サービスからの写しです（`price`、`duration` と同じ扱い）。

- 予約の消費税を、明細を足し、外すたびに、サービスに問い合わせずに算出し直すためです。サービスの設定は、明細を入れたあとで変わりうるので、サービスから読むと、残る明細の消費税が変わってしまいます
- 以前の行は、いまのサービスの `taxIncluded` で埋めます。明細を入れた時点の値は、残っていないからです（シードでは一致します）
- `BookingServiceResponse` に `taxIncluded` を加えました。リクエストには書けません

マイグレーション `202611160600_opening_hours_one_row_per_date.sql` で、営業日カレンダー（`opening_hours`）に、サロンと日付の一意インデックス（`opening_hours_salon_date_unique`）を加えました。

- 「1 つの日付に 1 件」は、サロンの作成と更新のリクエストの規則でしたが、テーブルは保証していませんでした。空き枠は、その日付の 1 行だけで営業時間を決めるので、2 行あると、どちらを読むかが決まりません
- 以前の行に、同じサロンの同じ日付の行が複数あれば、最後に書かれた行（`updatedAt` が新しい行。同じなら `id` が大きい行）を残して、ほかを削除します
- サロンの更新は、サロンの行をロックしてからカレンダーを入れ替えるので、同時に届いた 2 つの更新が、このインデックスに違反することはありません

スタッフの占有（重なり）は、DB の制約では保証しません。同時に受けられる数と前後の時間がスタッフごとに違い、制約では書けないからです。予約を書くトランザクション（作成、日時の変更、明細の追加）が、スタッフの行のロックで保証します。予約の日時と金額が明細の合計と合っていることも、制約では保証しません（2 つのテーブルにまたがる）。予約と明細を書くトランザクションが、予約の行のロックで保証します。

## シード

`pnpm db:seed` は、2 つのサロンに 16 件の予約を入れます（`backend/packages/database/src/seeds/seed-data/bookings.ts`）。

- 内容は、実行した日を基準に決まります（30 日前から 7 日後まで）。乱数は使いません
- 済んだ来店が 6 件（`completed`）、前日にキャンセルした予約が 1 件（`cancelled`）、前日に顧客が来店しなかった予約が 1 件（`no_show`）、これからの予約が 8 件（`confirmed` が 2 件、`pending` が 6 件）
- 済んだ予約とキャンセルした予約には、ステータスに伴う値があります（完了日時と完了した明細、キャンセル日時とキャンセル料 0）
- スタッフとサービスは、予約のサロンのものです。明細の時間と金額、税込かどうかはサービスの写しで、予約の時間と金額は明細から算出します。来店日は、サロンのタイムゾーンの日付です
- 予約番号は `BK-SEED-0001` から `BK-SEED-0016` です（API が採番する番号と同じ形式）
- どの予約にも、作成からのステータスの履歴があります
- 顧客の来店回数、キャンセル回数、無断キャンセル回数、初回と最終の来店日は、予約を入れたあとで、予約から数えます（顧客のシードには書きません）
- スタッフの占有の規則を満たします。同時に 2 件を受けるスタッフ（`STF001`）に、同じ時間の予約が 2 件あります
- レビューのシードは、済んだ来店のうち最初の 5 件に、その予約の顧客、サロン、担当スタッフで書きます。サロンの評価とレビュー件数は、そのあとで、レビューから数えます（[レビュー](./reviews.md#シード)）
- シードのサロンには営業時間が、スタッフには勤務スケジュールがあるので、空き枠の一覧は、これからの日付に枠を返します。シードの予約がある時間は、枠から除かれます
