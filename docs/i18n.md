# 多言語（i18n）

何を、どの言語で言うか。言語をどう決め、メッセージをどこに置くかを説明します。仕組みと
メッセージの定義は、パッケージ `@beauty-salon-shared/i18n`（`shared-i18n/`）にあります。

## 概要

- 言語は、英語（`en`）と日本語（`ja`）です。
- API は、リクエストの `Accept-Language` に合う言語で、エラー（problem details）の `title` と
  `detail` を返します。検証のエラーでは、決まりごとの `errors[].message` も、その言語です。
  どの言語で返したかは、`Content-Language` に書きます。
- ヘッダーのないリクエスト、API の言語を 1 つも言わないリクエストには、英語で返します。
- メッセージは、すべての言語の文を 1 つの値に持ちます。片方の言語が欠けると、型の検査で
  失敗します。訳の抜けは、実行する前に見つかります。
- 値（数、金額、日、時刻）の書き方も、言語で変わります。書式も、すべての言語の文を返します
  （[値の書き方](#値の書き方)）。
- 成功の応答（データ）とログは、言語で変わりません。ログは、いつも英語です。
- 画面にも、言語が 1 つあります。訪れた人が選んだ言語で、選んでいなければ日本語です。画面は、
  API へのどのリクエストにも、その言語を `Accept-Language` で付けます。
- 画面の文言は、すべての言語で書いてあります。フロントエンドの共有のパッケージと、ポータル、
  ダッシュボード、管理画面のすべての画面です（[画面の言語](#画面の言語)）。

## 言語の決め方

`localeOfAcceptLanguage(header, fallback)` が、`Accept-Language` の値から言語を決めます
（RFC 9110 の 12.5.4）。

1. ヘッダーを `,` で分け、1 つずつ、言語の範囲と重み（`;q=`）として読む。重みは 0 から 1 で、
   小数は 3 桁まで。書いていなければ 1。文法に合わない要素は、ないものとする
2. 重みが 0 より大きい範囲を、重みの大きい順に、同じ重みなら書いてある順に試す。製品の言語を
   言う最初の範囲で決まる
3. 範囲が言う言語は、タグの最初の部分で決める。`ja-JP` も `ja-Jpan-JP` も日本語。大文字と
   小文字は区別しない。製品の言語は、地域も文字の種類も付けずに書くので、RFC 4647 の 3.4 の
   Lookup が範囲を短くしていって行き着くのは、最初の部分
4. 重みが 0 の範囲は、その言語を受け取らないという意味。何も決めない。どの範囲でも
   決まらないときに、既定の言語がその言語なら、もう一方の言語にする
5. `*` は、言語を言わない。ヘッダーがないとき、どの範囲でも決まらないときは、既定の言語
   （`fallback`）。`Accept-Language` は希望で、合わないからといって、リクエストを断らない

| `Accept-Language` | 既定が英語のとき |
|---|---|
| （なし） | 英語 |
| `ja` | 日本語 |
| `ja-JP,ja;q=0.9,en;q=0.8` | 日本語 |
| `en-US,en;q=0.9,ja;q=0.8` | 英語 |
| `en;q=0.5,ja;q=0.6` | 日本語 |
| `fr-FR,fr;q=0.9` | 英語 |
| `*` | 英語 |
| `en;q=0` | 日本語 |
| `ja_JP`（文法に合わない） | 英語 |

既定の言語は、パッケージが決めません。呼ぶ側が渡します。API は英語です。

## すべての言語で書いた文

```typescript
// shared-i18n/src/languages/localized-text.ts
export type LocalizedText = Readonly<Record<Locale, string>>

export const text = (written: LocalizedText): LocalizedText => written

export const textIn = (written: LocalizedText, locale: Locale): string =>
  written[locale]
```

- メッセージは、`text({ en: '…', ja: '…' })` で書きます。`ja` を書き忘れると、コンパイル
  できません。
- 値で変わるメッセージは、値を受け取って `LocalizedText` を返す関数です。

```typescript
// shared-i18n/src/messages/api/problems.ts（抜粋）
export const problemMessages = {
  forbidden: {
    title: text({
      en: 'Forbidden',
      ja: '許可されていません',
    }),
    detail: text({
      en: 'This account is not allowed to do this',
      ja: 'このアカウントでは、この操作はできません',
    }),
  },
  routeNotFound: {
    title: text({
      en: 'Route not found',
      ja: 'ルートが見つかりません',
    }),
    detail: (method: string, path: string) =>
      text({
        en: `${method} ${path} is not part of the API`,
        ja: `${method} ${path} は、この API にありません`,
      }),
  },
  // ...
}
```

- 読む側は、言語を決めてから `textIn(message, locale)` で、その言語の文字列にします。

## 値の書き方

数、金額、日、時刻は、言語で書き方が変わります（「2026年11月20日（金）」と
`Fri, November 20, 2026`）。書式は `@beauty-salon-shared/i18n/formats` にあり、メッセージと
同じく、すべての言語の文（`LocalizedText`）を返します。言うのは、表示する所です。メッセージは、
書式の文を部品にして組み立てられます。

| 書式 | 値 | 日本語 | 英語 |
|---|---|---|---|
| `numberOf(value, decimals?)` | 数（`number` か `bigint`）。小数のけたは `{ most, least? }` で、書かなければ 3 けたまで | 1,234.5 | 1,234.5 |
| `percentOf(percentage, decimals?)` | API が百分率で書く割合（`12.5`） | 12.5% | 12.5% |
| `placeOf(place)` | 順位（1 から数える）。英語は序数 | 1 位、22 位 | 1st、22nd |
| `amountOf(amount, currency)` | 金額。通貨は ISO 4217 の符号 | ￥5,500 | ¥5,500 |
| `shortAmountOf(amount, currency)` | 場所のない所（チャートの軸）の金額 | ￥2.5万 | ¥25K |
| `currencyNameOf(currency)` | 通貨の名前。名前のない符号は、符号のまま | 日本円 | Japanese Yen |
| `bytesOf(size)` | ファイルの大きさを、1 バイトまで | 1,258,291 バイト | 1,258,291 bytes |
| `fileSizeOf(size)` | ファイルの大きさを、ひと目で読める単位で。1 KB（1,024 バイト）より小さければバイト、1 MB より小さければ KB の整数、そこからは MB の小数 1 けた | 340 KB、1.2 MB | 340 kB、1.2 MB |
| `monthOf(month)` | 暦の月（`2026-11`。API が月の集計に付ける名前） | 2026年11月 | November 2026 |
| `dayOf(day)` | 暦の日（`2026-11-20`） | 2026年11月20日 | November 20, 2026 |
| `dayWithWeekdayOf(day)` | 暦の日と曜日 | 2026年11月20日（金） | Fri, November 20, 2026 |
| `fullDayOf(day)` | 暦の日と、曜日の名前 | 2026年11月20日金曜日 | Friday, November 20, 2026 |
| `monthDayOf(day)` | 年を言わない暦の日と曜日 | 11月20日（金） | Fri, November 20 |
| `shortDayOf(day)` | 場所のない所（週の列）の暦の日 | 11/20（金） | Fri, 11/20 |
| `numericDayOf(day)` | 数字だけの暦の日（チャートの軸） | 2026/11/20 | 11/20/2026 |
| `timeOfDayAt(moment, timeZone)` | 時点（ISO 8601）の、時間帯の時計の時刻 | 09:05 | 09:05 |
| `momentAt(moment, timeZone)` | 時点の日と時刻 | 2026年11月20日 9:05 | November 20, 2026 at 09:05 |
| `momentWithWeekdayAt(moment, timeZone)` | 時点の日と曜日と時刻 | 2026年11月20日（金） 09:05 | Fri, November 20, 2026 at 09:05 |
| `timeRangeAt(from, to, timeZone)` | 2 つの時点の、時間帯の時計の時刻の範囲（予約の時間） | 10:30〜11:30 | 10:30–11:30 |
| `timeRangeOf(from, to)` | 2 つの時刻の範囲を、受け取ったままの時刻で（シフトの勤務と休憩。秒を見せる画面は、秒のある時刻を渡す） | 09:00〜20:00 | 09:00–20:00 |
| `timeSlotsOf(slots)` | API が書く 1 日の時刻の範囲（`{ startTime, endTime }` の並び。秒は書かない。営業時間、好みの時間帯） | 10:00〜12:00、14:00〜16:00 | 10:00–12:00, 14:00–16:00 |
| `durationOf(minutes)` | 分で数えた長さ（施術の所要時間） | 1 時間 30 分 | 1 hr 30 min |
| `minutesOf(minutes, decimals?)` | 分で数えた長さを、分だけで（分で入れるフォームと同じ書き方。管理画面のメニューと施術記録）。小数は、受け取ったけた数まで（施術時間の平均の `{ most: 1 }`）で、なければ 3 けたまで | 90 分、72.5 分 | 90 min、72.5 min |

- 暦の日は、時点ではないので、時間帯なしで書きます。読む所の時間帯で、日は変わりません。
  時点は、受け取った時間帯（サロンの時間帯か、読む人の時間帯）の時計で書きます。
- 時刻は、英語も 24 時間制です。API が書く 1 日の時刻（`10:00`、営業時間）と並ぶからです。
- 時刻の範囲は、日本語は「〜」で、英語は en ダッシュ（`–`）でつなぎ、範囲の並びは、日本語は「、」で、
  英語は「, 」で区切ります。長さの単位は、`Intl` が言語ごとに書きます（`hr`、`min`、「時間」「分」）。
- 日本語の曜日は、全角の括弧で囲みます。`Intl` は半角の括弧で書くので、言語ごとに組み立てます。
- `Intl` の書式は、作るのに、値を 1 つ書くことの約 50 倍かかり、値はどの言語でも書くので、
  言語と設定ごとに 1 つ作って持ちます（`formats/formatters.ts`）。
- 数を数える言葉（件、回、ポイント）と単位（`bottle`）は、書式ではなく、文言です。書式の
  数を入れて、メッセージが言います。ファイルの大きさの単位（バイト、KB、MB）は、`Intl` が
  言語ごとに書くので、書式です。
- メッセージが値を入れるときも、書式で書きます。共通の部品のメッセージの数（数え方、条件の数、
  評価の件数）は `numberOf` で、評価の値は、評価の部品が小数 1 けたで書いた書式を受け取ります
  （`uiMessages.rating.outOf(5, numberOf(4.5, { most: 1, least: 1 }), null)`）。
- 言語で変わらない使い方は、それぞれの所に残します。ISO の日付を作る `sv-SE`（サロンの日付、
  ブラウザーの日付）、時差を読む `en-US` の部品（サロンの時計の日時を UTC の時点にする）、
  ブラウザーの時間帯（`resolvedOptions().timeZone`）、ブラウザーが知る時間帯と通貨の一覧
  （`supportedValuesOf`）、フォームの欄が持つ値（サロンの緯度と経度の `toFixed(8)`）です。
- 名前の並べ替え（`localeCompare(…, 'ja')`）は、サロンが書いた名前の文字で決まるので、読む
  人の言語では変えません。
- 画面は、書式を `formats` の名前で読みます
  （`import * as formats from '@beauty-salon-shared/i18n/formats'`）。画面の関数
  （`amountOf`、`timeOfDayAt`）と、名前が重なりません。
- `salon-screens` の値の書き方（`amountOf`、`dayNameOf`、`timeOfDayAt`、`momentNameAt`、
  `periodNameOf`、`methodKindNameOf`、`categoryNameOf`）は、書式と業務の言葉のメッセージを
  返し、画面の部品が言います（`say(amountOf(sale.totalAmount, currency))`）。
- アプリの書式の関数も、メッセージを返します（ポータルの `salon-format.ts`、`booking-format.ts`、
  `profile-format.ts`、`review-format.ts`、`shared-file.ts`、ダッシュボードの `sales-report.ts`、
  `sales-trends.ts`、管理画面の `customer-format.ts`、`share-link.ts`、`attachment-file.ts` など:
  `whenLineOf`、`priceLineOf`、`totalOf`、`subjectOf`、`sizeNameOf`、`partNameOf`、
  `axisAmountOf`）。書式を言い換えるだけの関数（会員ランクや性別の名前、ダッシュボードの件数と
  順位）は置かず、業務の言葉や書式を直接言います（`dashboardReportMessages.count`、
  `formats.placeOf`）。
- 管理画面の量（在庫、使った量、発注の数）は、API が持つ小数 2 けたまでで書きます。量の書き方は、
  `frontend/apps/admin-app/src/products/utils/quantity.ts` の `quantityOf` だけにあります。
- テストの用意（`__tests__/arrangements`）は、期待する文を、自分で `Intl` で作ります。確かめる
  コードと同じ書式で期待を作ると、書式の誤りを見つけられません。

## API のエラーの言語

API のエラーの応答は、すべて `sendProblem`（`backend/packages/api/src/shared/responses.ts`）
が送ります。言語を決めるのも、ここだけです。

1. `languageAsked(req)`（`backend/packages/api/src/shared/language.ts`）が、リクエストの
   `Accept-Language` から、頼まれた言語を決める。既定は英語
2. `toProblemDetails`（`backend/packages/api/src/shared/problem-details.ts`）が、その言語の
   `title` と `detail` で、problem details を作る
3. 応答に、`Content-Language`（言った言語）を付け、`Vary` に `Accept-Language` を加える

どのエラーも、頼まれた言語で言います。エラーが運ぶ文は、どれも、すべての言語で書いてあります。

| エラー | `detail` を書く所 |
|---|---|
| `unauthenticated`（`reason` ごとに 5 つ）、`forbidden`、`passwordRequired`、`database`、`storage` と、HTTP の層のエラー（`routeNotFound`、`malformedBody`、`unsupportedMediaType`、`bodyTooLarge`、`badRequest`、`rateLimited`、`unexpected`） | API の層（`problemMessages`） |
| `validation` | ドメイン（見出しと、決まりごとの文） |
| `notFound`、`alreadyExists` | API の層（`problemMessages` の `detail`）。対象の名前は、ドメインが、すべての言語で渡す（`entityMessages`） |
| `conflict` | ドメイン（領域のファイルのメッセージ）。API の層は、その文をそのまま言う |

- 1 つの応答に、2 つの言語を混ぜません。ドメインがエラーに載せる文（見出し、決まりごとの文、
  対象の名前、できない理由）は、型が、すべての言語の文（`LocalizedText`）です。文字列で書くと、
  コンパイルできません。
- 言語で変わるのは、`title`、`detail` と、`errors` の `message` だけです。`type`、`status`、
  `code`、`errors` の `field` と `rule` は、変わりません。クライアントは、文ではなく `code` と
  `rule` で分岐します。
- 成功の応答には、`Content-Language` も `Vary: Accept-Language` も付けません。
- 原因をログに書くとき（`database` と `storage`）の文は、英語のままです。

契約（`specs/models/_shared/common-api-patterns.tsp`）では、エラーの応答 `ProblemResponse`
に `Content-Language` のヘッダーがあり、値は列挙 `LanguageType`（`en`、`ja`）です。
`Accept-Language` は、オペレーションごとの引数にしていません。引数にすると、生成される
クライアントのすべての関数に引数が増えます。リクエスト ID の `X-Request-Id` と同じ扱いです。

`sendProblem` は、言う言語を、契約の `LanguageType` の型の変数に入れてからヘッダーに
書きます。パッケージに言語を足して、契約に足し忘れると、コンパイルできません。

```http
GET /api/v1/stylists HTTP/1.1
Accept-Language: ja-JP,ja;q=0.9,en;q=0.8

HTTP/1.1 404 Not Found
Content-Type: application/problem+json; charset=utf-8
Content-Language: ja
Vary: Origin, Accept-Language, Accept-Encoding

{
  "type": "urn:beauty-salon:problem:route-not-found",
  "title": "ルートが見つかりません",
  "status": 404,
  "detail": "GET /api/v1/stylists は、この API にありません",
  "code": "3001",
  ...
}
```

## 検証のエラー

検証のエラー（`validation`、400）は、4 つの所が文を書きます。見出し（`detail`）と、
決まりごとの文（`errors[].message`）を言う、Zod、スキーマ、ユースケースです。4 つとも、
すべての言語で書きます。

```http
POST /api/v1/salons HTTP/1.1
Accept-Language: ja

HTTP/1.1 400 Bad Request
Content-Language: ja

{
  "title": "入力の内容が正しくありません",
  "detail": "サロンの内容が正しくありません",
  "errors": [
    { "field": "name", "rule": "invalid_format", "message": "空白だけにはできません", ... },
    { "field": "taxRate", "rule": "invalid_type", "message": "無効な入力: 数値が期待されましたが、stringが入力されました", ... },
    { "field": "colour", "rule": "unrecognized_keys", "message": "このプロパティは指定できません", ... }
  ],
  ...
}
```

### 見出し

見出しは、領域のファイル（`shared-i18n/src/messages/api/<領域>.ts`）のメッセージです。
ユースケース、ID を読む関数（`models/<領域>.ts`）、クエリを読む関数
（`api/src/routes/<領域>/_shared/query.ts`）が、`parseWith` に渡します。

```typescript
// backend/packages/domain/src/business-logic/salon/create-salon.usecase.ts
const request = parseWith(
  salonCreateRequestSchema,
  input,
  salonMessages.invalidSalon,
)
```

- 見出しは、その実体の領域のファイルに 1 つだけ置きます。複数の領域が同じ見出しを言うときも
  同じです（`customerMessages.invalidCustomerId` は、顧客、アレルギー、カルテの ID を読む関数が
  使います。予約の見出しは、`booking` と `customer-booking` のユースケースが使います）。
- 見出しを受け取って検証のエラーを作る共有の関数（`toRefusalError`、`salonNotFound`、
  `mailedTokenRefused` など）も、メッセージ（`LocalizedText`）を受け取ります。見出しを
  文字列で書くと、コンパイルできません。

### Zod が言う文

型、長さ、形式など、Zod の決まりの文は、Zod が言います。Zod は、検査のたびに、文の言語を
受け取れます。`parseWith`（`backend/packages/domain/src/shared/validation.ts`）は、決まりに
合わない入力を、Zod の日本語の文（`zod/locales` の `ja`）で、もう一度検査します。同じ入力を
同じスキーマで検査するので、2 つの結果は、同じ決まりが、同じ順に並びます。同じ位置どうしを、
1 つの文の英語と日本語にします。

- 2 回目の検査は、決まりに合わない入力のときだけです。合う入力は、1 回です。
- スキーマは、時刻や乱数を見ません。見ると、2 つの結果が同じ並びになりません。いまを基準に
  する決まりは、時計を受け取るユースケースが確かめます。
- 契約にないプロパティ（`unrecognized_keys`）は、Zod の文を使いません。プロパティごとに
  1 つずつ、そのプロパティの名前を `field` にして、`ruleMessages.unknownProperty` を言います。

### スキーマが書く文

スキーマが決まりに付ける文は、スキーマに書いた文が、Zod の言語の指定より先に使われます。
言語ごとに変えられないので、その文に、すべての言語を持たせます。Zod が運ぶ文は文字列だけ
なので、すべての言語の文を、1 つの文字列にして渡します。

```typescript
// backend/packages/domain/src/schemas/rules.ts
export const nonBlankText = z
  .string()
  .regex(/\S/, asOneString(ruleMessages.notBlank))
```

```typescript
// shared-i18n/src/languages/one-string.ts
export const asOneString = (written: LocalizedText): string =>
  [written.en, written.ja].map(withoutSeparator).join(BETWEEN_LANGUAGES)

export const textOfOneString = (string: string): LocalizedText | undefined => { ... }
```

- 言語の間は、制御文字の U+001F（unit separator）です。文には出てこない文字です。値を
  入れて作る文（`ruleMessages.laterThan('openTime')`）の値にその文字があれば、空白にします。
- `parseWith` が、`textOfOneString` で読み戻します。1 つの文字列にした文は、`parseWith` の
  外には出ません。ドメインのスキーマを `safeParse` で直接使って、文を読む所はありません。
- 複数の領域が共有する決まりの文は、`ruleMessages`（`rules.ts`）にあります。プロパティの
  名前を入れる文は、名前を受け取る関数です（`laterThan('startTime')`、
  `notEarlierThan('startDate')`）。プロパティの名前は、どの言語でも、リクエストに書く
  名前のままです。
- クエリの引数の型の文（`Must be a number`、`Must be true or false`）も、`ruleMessages` です
  （`backend/packages/api/src/shared/query-parameters.ts`）。
- 領域の決まりの文は、その領域のファイルにあります。値で変わる文は、値を受け取る関数です
  （`salesReportMessages.withinDaysOfStartDate(MAX_REPORT_DAYS)`、
  `inventoryAlertMessages.nullForProductAlert(alert)`）。
- スキーマとユースケースが同じ決まりを言うときは、同じメッセージを使います。支払い方法の
  上限と下限（`LIMITS_OUT_OF_ORDER`）、商品の在庫水準（`stockLevelIssues`）、顧客のいない
  売上のポイント（`saleMessages.noPointsWithoutCustomer`）です。スキーマは `asOneString` で
  渡し、ユースケースは、メッセージをそのままエラーに入れます。
- スキーマのソースに、文を文字列で書くと、テストが失敗します
  （`backend/packages/domain/src/schemas/__tests__/schema-messages.test.ts`）。2 語以上の
  文字列、文の始まり方をする文字列（大文字の次が小文字）、`asOneString` を通さない `message`
  を、ソースから探します。
- 日本語の文は、文末に「。」を付けません。「〜にしてください」（英語の `Must be …`）、
  「〜にはできません」「〜は指定できません」（`Must not …`）と書きます。

### ユースケースが作る文

スキーマでは確かめられない決まりは、ユースケースと、その `_shared/` の関数が確かめます。
参照先がない（`not_found`）、保存してある行と合わない、いまの時刻を基準にする、などです。
その文も、メッセージです。Zod を通らないので、メッセージをそのままエラーに入れます。

```typescript
// backend/packages/domain/src/business-logic/booking/list-bookings.usecase.ts
DomainErrors.validation(MESSAGE, [
  {
    field: 'cursor',
    rule: 'not_found',
    message: bookingMessages.aBooking,
  },
])
```

- 決まりごとの文の型（`ValidationIssue` の `message`）は、`LocalizedText` です。文字列は、
  コンパイルできません。
- 1 つの領域だけが言う文は、その領域のファイルに置きます。2 つ以上の領域が言う文は、
  `ruleMessages` に置きます（`aSalon`、`aCustomer`、`aStaffMemberOfSalon`、`notInFuture` など）。
- 「〜を指定してください」（`Must name a …`）の文は、指定するものの名前で呼びます
  （`aCustomer`、`aStockRowOfSalon`）。`notFound(field, message)`
  （`business-logic/booking/_shared/plan.ts`）が、その文で、`not_found` の決まりを作ります。
- 値を言う文は、値を受け取る関数です（`paymentMessages.notMoreThanLeftToPay(left)`、
  `ruleMessages.notEarlierThan(earliest)`）。
- 文を運ぶ関数と、リポジトリの結果も、文字列ではなく、メッセージを運びます
  （`lotNumberRefusal` と、在庫のリポジトリの `lotNumberRefused`）。
- 日本語の文は、リクエストが指すものを「この」で言います（`Must name a staff member of the salon` は
  「このサロンのスタッフを指定してください」）。どこにもないものを指す ID には、「存在する〜」と
  言います（`Must name a salon` は「存在するサロンを指定してください」）。

### 文の型

検証のエラーが運ぶ文は、どれも、すべての言語の文（`LocalizedText`）です。見出し
（`DomainErrors.validation` と `parseWith` の `message`）も、決まりごとの文
（`ValidationIssue` の `message`）も、文字列で書くと、コンパイルできません。

- `parseWith` は、スキーマが文字列で書いた文も、どの言語でも同じ文として返します。
  リクエストのスキーマに、そういう文はありません（`schema-messages.test.ts`）。

| 文 | 書く所 | 言語 |
|---|---|---|
| 見出し | 領域のファイルのメッセージ（すべての領域） | すべての言語 |
| Zod が言う文 | Zod（`parseWith` が両方の言語で取り出す） | すべての言語 |
| スキーマが書く文 | 領域のファイルと `rules.ts` のメッセージ（すべての領域） | すべての言語 |
| ユースケースが作る決まりごとの文（スキーマでは確かめられない決まり: 参照先がない、保存してある行と合わない、など） | 領域のファイルと `rules.ts` のメッセージ（すべての領域） | すべての言語 |

### 保存してある値

データベースから読んだ値（文字列で返る `numeric` と `timestamptz`、`jsonb`）がモデルに
合わないのは、リクエストの誤りではありません。検証のエラーには、しません。読むときの
マッパーと、セッションから操作者を作る所は、`parseStored(schema, stored, description)`
（`backend/packages/domain/src/shared/validation.ts`）で読みます。合わないときは、
データベースのエラー（500）が返ります。

```typescript
// backend/packages/domain/src/mappers/read/product.mapper.ts
parseStored(
  convertedColumnsSchema,
  product,
  `Stored product ${product.id} does not match the API model`,
)
```

- `description` は、ログに書く英語の文です。どの行の話かを言います。ほかの行と一緒に読む行
  （予約のサービス、売上の明細と支払い、発注の品目、施術の材料、在庫のアラートの確認）には、
  読む側のマッパーが、その文を渡します。
- 原因（`cause`）は、合わなかったプロパティと決まりです（`field`、`rule`、英語の `message`）。
  保存してある値は、入りません。`sendProblem` が、ログに書きます。
- 応答に、文は出ません。`title` は、頼まれた言語の「サーバーでエラーが起きました」で、
  `detail` は `null` です。
- 検証のエラーを作ってから、データベースのエラーに包み直すことは、しません。包み忘れると、
  保存してあるデータの誤りに、400 を返すことになります。

## 見つからない、すでにある

「見つからない」（`notFound`、404）と「すでにある」（`alreadyExists`、409）のエラーは、対象の
名前を、すべての言語で運びます。文は、API の層が、名前と、ID や値から、頼まれた言語で
作ります。

```typescript
// backend/packages/domain/src/shared/errors.ts
| { type: 'notFound'; entity: LocalizedText; id: string | null }
| { type: 'alreadyExists'; entity: LocalizedText; field: string; value: string }

// backend/packages/domain/src/business-logic/salon/get-salon.usecase.ts
DomainErrors.notFound(entityMessages.salon, salonId.data)

// backend/packages/infrastructure/src/repositories/salon.repository.impl.ts
DomainErrors.alreadyExists(entityMessages.salon, 'email', violation.email)

// backend/packages/api/src/shared/problem-details.ts
detail: said(problemMessages.notFound.detail(entity, id)),
```

| エラー | 英語 | 日本語 |
|---|---|---|
| `notFound` | `Salon <id> was not found` | 「サロンが見つかりません（ID: <id>）」 |
| `notFound`（`id` が `null`） | `Share link of the token was not found` | 「このトークンの共有リンクが見つかりません」 |
| `alreadyExists` | `Salon with email <値> already exists` | 「email が <値> のサロンは、すでにあります」 |

- 対象の名前は、`shared-i18n/src/messages/api/entities.ts` の `entityMessages` です。領域の
  ファイルではなく、1 つのファイルに置きます。同じ名前を、いくつもの領域が言うからです
  （サロン、顧客、スタッフ）。
- 名前の型は `LocalizedText` です。文字列は、コンパイルできません。
- 英語の名前は、これまで API が言ってきた名前のままです。`TreatmentRecord` と `Staff member` の
  ように、書き方がそろっていない名前も、そのままです。応答の英語の文を変えないためです。
- 持ち主を言う名前（`accountOfStaffMember`、`customerProfileOfUser`、
  `deletionRequestOfCustomer` など）は、持ち主の ID で探したものです。英語では、ID が持ち主に
  続きます（`Account of staff member <id> was not found`）。日本語では、名前が「この ID の〜」と
  言います（「この ID のスタッフのアカウントが見つかりません（ID: <id>）」）。
- 値で変わる名前は、値を受け取る関数です（`entityMessages.versionOfCustomer(version)`）。
- `notFound` の `id` は、探すのに使った ID です。繰り返さないもので探したとき（共有リンクの
  トークン）は `null` で、文に ID は出ません。
- `alreadyExists` の `field` は、リクエストのプロパティの名前で、どの言語でも、そのままです。
  `value` も、そのままです。
- `alreadyExists` の文は、どの言語でも、値を空白の間に置きます。管理画面の、顧客の CSV の
  登録が、文の中から、重なった値を、空白で区切った語として探すからです
  （`frontend/apps/admin-app/src/customers/utils/customer-file.ts`）。
- 領域の文書（`docs/customers.md` など）は、`detail` を英語の文で書いています。日本語を
  頼むと、同じことを、上の形の日本語で言います。

## いまの状態ではできない

「いまの状態ではできない」（`conflict`、409）のエラーは、できない理由の文を、すべての言語で
運びます。文は、ドメインが、領域のファイルのメッセージで言います。API の層は、その文を、
頼まれた言語で、そのまま `detail` にします。

```typescript
// backend/packages/domain/src/shared/errors.ts
| { type: 'conflict'; message: LocalizedText }

// backend/packages/domain/src/business-logic/sale/void-sale.usecase.ts
DomainErrors.conflict(saleMessages.alreadyVoid)

// backend/packages/domain/src/business-logic/booking/_shared/change-status.ts
DomainErrors.conflict(bookingMessages.statusDoesNotAllow(action, status, allowed))

// backend/packages/api/src/shared/problem-details.ts
detail: said(message),
```

```http
DELETE /api/v1/customers/bulk HTTP/1.1
Accept-Language: ja

{ "ids": ["<ID>"] }

HTTP/1.1 409 Conflict
Content-Language: ja

{
  "type": "urn:beauty-salon:problem:operation-not-allowed",
  "title": "この操作はできません",
  "status": 409,
  "detail": "顧客 <ID> は削除できません。終わっていない予約が参照しています",
  "code": "3003",
  ...
}
```

| 文 | 英語 | 日本語 |
|---|---|---|
| 書いてある文（`saleMessages.alreadyVoid`） | `The sale is void already` | 「この売上は、すでに取り消されています」 |
| 値を言う文（`customerMessages.unfinishedBookingsReferTo(customerId)`） | `Customer <id> cannot be deleted: bookings that are not finished refer to it` | 「顧客 <id> は削除できません。終わっていない予約が参照しています」 |
| 状態を言う文（`bookingMessages.statusDoesNotAllow('complete', 'cancelled', ['confirmed', 'in_progress'])`） | `A booking that is cancelled cannot be completed; its status has to be confirmed or in_progress` | 「状態が cancelled の予約は、完了できません。状態は、confirmed か in_progress でなければなりません」 |
| 並べる文（`bookingMessages.referredTo(['sale', 'treatmentRecord', 'review'])`） | `The booking cannot be deleted: a sale, a treatment record and a review refer to it` | 「この予約は削除できません。売上と施術記録とレビューが参照しています」 |

- 文は、その文が言うものの領域のファイル（`shared-i18n/src/messages/api/<領域>.ts`）に
  置きます。予約のことを言う文は、顧客が自分の予約を動かすユースケース
  （`customer-booking`）が言うときも、`bookingMessages` です。
- `message` の型は `LocalizedText` です。文字列は、コンパイルできません。
- 英語の文は、これまで API が言ってきた文のままです。
- 値（状態の名前、ID、数、プロパティの名前、アドレス）は、どの言語の文にも、そのまま
  出します。状態の名前（`in_progress`）は、契約の値なので、訳しません。
- 値を言う文は、値を受け取る関数です。言語で変わるもの（並べ方、単数と複数、動作の名前）は、
  メッセージの中で、言語ごとに作ります。ユースケースは、文の部品（`a sale`、`and`）を
  渡しません。渡すのは、値と、何のことかの名前です。
  - `bookingMessages.statusDoesNotAllow(action, status, allowed)`: `action` は、動作の名前
    （`'complete'`）。英語は `completed`、日本語は「完了」と言います。許される状態は、英語は
    `or`、日本語は「か」で並べます。
  - `bookingMessages.referredTo(by)`: `by` は、参照しているものの名前（`'sale'`）。英語は
    `a, b and c` と並べ、1 つなら `refers` と言います。日本語は「と」で並べます。
  - `purchaseOrderMessages.notFromStatus(id, status, operation)`: `operation` は、頼まれた
    操作の名前（`'approval'`）。文の終わりが、その操作が受け付ける発注を言います。
- 日本語の文は、文末に「。」を付けません。2 つの文からなるときは、間にだけ付けます。
- 日本語の言葉は、API のほかの文の言葉にそろえます（顧客、スタッフ、売上、支払い、発注、
  施術記録、カルテ）。API がまだ言っていなかった言葉は、画面の言葉にそろえます（売上の
  void は「取り消し」、no-show は「無断キャンセル」、レポートの dismiss は「却下」、
  在庫の reserved は「引当済み」、データの erase は「消去」）。
- 文を運ぶ関数も、文字列ではなく、メッセージを運びます（添付ファイルの `refusalOf`、
  発注の `toStatusConflict`、終わっていない予約の `unfinishedBookingsReferTo`）。リポジトリの
  実装が言う 1 つの文（顧客のプロフィールの登録が重なった）も、メッセージです
  （`customerMessages.registeredAtSameMoment`）。
- 画面は、409 を、文ではなく、`code` と、読み直した状態で見分けます。文を読む画面は
  1 つです。管理画面の、顧客のまとめての削除が、文の中から、選んだ顧客の ID を探します
  （`frontend/apps/admin-app/src/customers/api/customer-bulk-api.ts`）。その文
  （`customerMessages.unfinishedBookingsReferTo`）は、どの言語でも、ID をそのまま言います。
- 領域の文書（`docs/bookings.md` など）は、`detail` を英語の文で書いています。日本語を
  頼むと、同じことを、日本語で言います。

## 画面の言語

画面にも、言語が 1 つあります。訪れた人が選んだ言語で、選んでいなければ日本語です。

| 何を | どこで | どうする |
|---|---|---|
| 選択を保つ | `frontend/packages/io/src/libs/language/stored-language.ts`（`languageStore`） | ブラウザーの `localStorage` の `beauty-salon:language`。値がない、製品の言語でない、ブラウザーが保存を断る、のどれでも、日本語。同じタブの選択も、ほかのタブの選択（`storage` イベント）も、聞き手に伝える |
| API に頼む | `frontend/packages/api-client/src/fetcher/`（`fetcher.ts`、`renew-session.ts`） | どのリクエストにも、ページの言語を `Accept-Language` で付ける。呼ぶ側が書いた値より優先する。セッションを再発行するリクエストも同じ。API のエラーの文は、ブラウザーの言語ではなく、ページの言語で返る |
| 文書の言語 | `frontend/packages/app-frame/src/utils/page-language.ts`（`startApplication` が呼ぶ） | `<html lang>` を、ページの言語に合わせ続ける。読み上げと、書体の選択のため |
| 文を言う | `frontend/packages/ui/src/hooks/language.ts`（`useSay`） | 部品が、メッセージを、ページの言語で言う。言語が変わると、描き直して、言い直す。プロバイダーは要らない（`useSyncExternalStore` で、保つ所を読む） |

- 画面の既定が日本語なのは、画面が日本語で書かれてきたからです。API の既定（英語）とは
  別に決めています。
- 言語を選ぶ部品は、まだ、どのアプリにも出していません。選択を書くのは、テストと Storybook
  だけです。

### 画面の文言

画面の文言は、すべての言語で書いたメッセージです。`ui`、`fields`、`answers`、`session`、
`app-frame`、`salon-screens`、`preferences` と、ポータル、ダッシュボード、管理画面のすべての
画面とヘッダーのリンクが、そうです（文言を持たない `io` と `api-client` も、確かめます）。

パッケージとアプリの決まり:

1. 文言は、`shared-i18n/src/messages/<だれが言うか>/` のメッセージです（共通の部品は
   `ui/components.ts` の `uiMessages`、入力の決まりは `ui/fields.ts` の `fieldMessages`、応答の
   読み方は `ui/answers.ts` の `answerMessages`、セッションの画面は `ui/session.ts` の
   `sessionMessages` と `ui/security.ts` の `securityMessages`、アプリの枠は `ui/frame.ts` の
   `frameMessages`、サロンの画面が共有する部分は `ui/salon-screens.ts` の `salonScreenMessages`、
   好み設定は `ui/preferences.ts` の `preferenceMessages`、お客様の記録の欄の名前は
   `ui/customers.ts` の `customerMessages`、ポータルは `portal/` の領域ごとのファイル、
   ダッシュボードは `dashboard/`、管理画面は `admin/`）。API のメッセージと同じく、`text({ en, ja })` で書き、値で変わる文は、値を
   受け取る関数にします。
2. 言うのは、表示する部品です。`const say = useSay()` のあと、`say(uiMessages.close)`。
   部品でないもの（値の決まり、応答の読み方、定数）は、メッセージのまま渡し、1 つの言語の
   文字列にしません。値の書式（[値の書き方](#値の書き方)）も、同じです。
3. `ui` の部品は、自分の文言（「閉じる」「必須」「さらに表示」など）だけを言います。画面が
   渡す文言（`label`、`title`、`message`、ボタンの中身）は、画面が言い終えた文字列です。
   通知（`notify`）だけは、メッセージを受け取り、表示する所で、そのときのページの言語で
   言います。
4. 数の文は、`ui` の数え方で作ります。`countOf(total, shown, COUNTED.items)` は、
   「12 件（10 件を表示しています）」と `12 items (showing 10)` を持つメッセージです。英語は、
   1 つのときに単数で言います（`1 item`）。
5. `fields` と `answers` は、名前をそのままに、メッセージを返します。決まりの関数
   （`emailError`、`tooLongError`）は、何も言うことのない値に `undefined` を返し、`lengthErrors`
   は、コントロールの名前ごとのメッセージを返します。文が何のことかを言う名前も、メッセージで
   受け取ります。
   - 入力の決まりの文（`tooLongOf(what, most)`、`neededWithin`、`eachTooLongOf`）の名前は、
     コントロールの名前です。英語は、名前を見出しのように前に置き、冠詞を付けません
     （`Supplier: enter up to 100 characters.`、「仕入先は、100 文字以内で入力してください。」）。
   - 読み込めなかったものの名前（`unreadMessageOf(what, reason)`）は、英語では、冠詞を
     含めた名詞句です（`the bookings` で `Could not load the bookings. …`）。
   - 文字数と行の番号は、値の書式（`numberOf`）で書きます（`2,000 characters`、「1,200 行目」）。
   - ほかのカタログの文の中に置く名前（読み込めなかったもの）は、カタログの `names` に置きます
     （`securityMessages.names.account`）。文の始まりではないので、英語は、小文字で始めます。
6. フォームは、メッセージを言います。
   - 値を読む関数と、答えを読む関数は、誤りと文を、メッセージで返します
     （`FormRead<Value, FormErrors<LocalizedText>>`、`FormSays<LocalizedText>`）。`aboutTheAttempt` と
     `errorAt` は、文字列もメッセージも、そのまま受け取ります。画面は、それを
     `useState<FormSays<LocalizedText>>(NOTHING_TO_SAY)` に保ちます。
   - フォームを表示する部品は、メッセージを受け取り（`message?: LocalizedText`、
     `errors?: FormErrors<LocalizedText>`）、`useSaidForm(message, errors)` で、ページの言語で
     言います。コントロールには、言った文（`said.errors[CODE]`）を、`Form` と `FormDialog` には、
     受け取ったままの誤り（`errors={errors}`）を渡します。
   - `Form` は、`errors` が新しいオブジェクトのとき（新しい試みのとき）に、誤りのある最初の
     コントロールへ、フォーカスを動かします。言った文は、描くたびに新しいオブジェクトなので、
     それを渡すと、言語が変わるたびに、フォーカスが最初の誤りへ飛びます。
   - `Form` と `FormDialog` の誤りの型は、型引数で、渡すものから決まります。書かなければ、
     言った文字列（`FormErrors`）です。検索の条件の `FilterForm`（集計の期間の `StatisticsPeriod`）も、受け取った
     ままの誤りを受け取り、時間帯の行のような、繰り返す行の誤り（`useRepeatedRows`）は、型引数で
     メッセージの誤りも受け取ります（`useRepeatedRows<ModelsTimeSlot | undefined, LocalizedText>`）。
   - 選択肢の名前がメッセージのとき（列挙の値を、その名前で出すとき）、部品でないものは、
     名前をメッセージで持つ選択肢（`ui` の `NamedChoice`）を返します。部品は、
     `const options = useSaidChoices()` のあと、`options(GENDER_CHOICES)` で、ページの言語の
     選択肢にします。お客様のフォームが出す性別とサービスの種類は、`fields` の
     `GENDER_CHOICES` と `CATEGORY_CHOICES` で、ポータルのプロフィールと管理画面の台帳が
     共有します。
   - 部品が、画面から受け取る文言は、画面が言い終えた文字列のままです（`KeywordSearch` の
     `label` と `description`、`StatisticsPeriod` の `description`）。ほかのサロンの画面を開いた
     スタッフへの通知（`OtherSalonNotice`）は、文の中に置く名前（`what`、`who`、`start`）を、
     メッセージで受け取ります。好みの表示（`PreferencesDetails`）は、スタッフの名前を、
     メッセージで受け取ります（`staffNames`）。
7. 業務の言葉（契約の列挙の値の名前）は、`ui/terms.ts` の `termMessages` に、値ごとに
   置きます（`termMessages.bookingStatus.confirmed`）。2 つ以上のアプリかパッケージが名前を
   言う列挙と、ファイルの種類の名前です。
   - 言語のパッケージは、生成した型に依存しません。画面は、名前の表を
     `Record<ModelsBookingStatusType, LocalizedText>` の定数に入れ、値の抜けを型の検査で
     見つけます。
   - 英語は、日本語の名前に合わせた、短く広く使われている言い方です（`Confirmed`、`No-show`、
     `Prefer not to say`、`Gold`、`Owner`、`Senior`）。どの言語でも同じに書く言葉（`VIP`、`PDF`）は、
     メッセージのテストの表 `WRITTEN_ALIKE` に書きます。
   - 予約の状態は、サロンの言葉です（`no_show` は「無断キャンセル」）。ポータルは、`no_show`
     だけを、お客様の言葉（`termMessages.notVisited`、「来店なし」）に替えます。お客様に
     「無断」とは言いません。
   - 1 つのアプリだけが名前を言う列挙（アレルギー、施術の種類、ポイントの取引、アカウントの
     状態など）は、そのアプリのメッセージです。
     レビューの通報の理由は、ポータル（通報のダイアログ）と管理画面（通報の一覧）が言うので、
     業務の言葉です（`termMessages.reviewReportReason`）。

  保存する」は `portalFrameMessages`）。
- リンクを含む文は、文の部分ごとのメッセージです（`…WithLink` の `before`、`link`、`after`。
  リンクが 2 つの文は、`…WithLinks` に、リンクごとの名前）。部品は、部分を順に言い、リンクの
  部分をリンクにします。どの言語も、部分を同じ順に並べて 1 つの文になるように書きます
  （`Sign in` と ` to say that a review was helpful, …`、「サインイン」と「すると、…できます。」）。
- ヘッダーのリンクは、アプリの枠が言います。アプリの `navigationFor` は、名前をメッセージで
  持つリンク（`app-frame` の `FrameLink`）を返し、`AppFrame` が、ページの言語で言います。
  管理画面の名前は、`adminFrameMessages.navigation` です。

  （お客様に語りかける部分、サロンがお客様をどう扱うか）は、それぞれのカタログに置きます。
- ポータルと管理画面が同じに言うレビューの言葉（評価の項目、評価ごとの件数、来店確認済み、写真、
  サロンからの返信、並び順、通報のダイアログの題と欄と誤り）は、`reviewMessages` です。お客様が
  レビューを書くフォームと、サロンの返信を書くフォームは、それぞれのカタログに置きます。
- 値の並びを区切る記号も、メッセージです（電話番号の間の
  `portalSalonMessages.about.betweenPhoneNumbers`、「、」と `, `）。
- 1 つのカタログの文が、別のカタログの文（読み込めなかったもの）の中に置く名前は、その
  カタログの `names` に置きます（`portalBookingMessages.names.freeTimes`）。

値を含む文は、カタログの関数が組み立てます
（`adminShareLinkMessages.form.errors.limit(formats.numberOf(MOST_DOWNLOADS))`）。画面は、メッセージを、
テンプレートリテラル、`+`、`join` に渡しません。渡すと、`[object Object]` になります。型の検査は、これを止めません。
エントリーが組でない `Object.fromEntries`（`any` を返します）と、レコードの展開（`...record`。
インデックスシグネチャーが落ちます）も、型の検査が見ない所です。フォームのエラーは、
テストが、文と比べて確かめます。

## メッセージを足す、言語を足す

API のエラーの種類を足すとき:

1. `DomainError` か `HttpError` にケースを足す（[Sum型とパターンマッチング](./sum-types-pattern-matching.md)
   の「ケースを追加するとき」）
2. `shared-i18n/src/messages/api/problems.ts` に、`title` と、API の層が書くなら `detail` を、
   両方の言語で足す
3. `problem-details.ts` の `toProblem` の `match` に分岐を足す（ステータス、`code`、文）。
   `.exhaustive()` なので、足すまでコンパイルできない
4. `problem-details.test.ts` の表に、両方の言語の文を足す

検証のエラーの文を足すとき:

1. 見出し、スキーマが書く文、ユースケースが作る文を、領域のファイル
   （`shared-i18n/src/messages/api/<領域>.ts`）に、両方の言語で足す。複数の領域が使う決まりの
   文は、`rules.ts` に足す。新しいファイルは、`messages/api/index.ts` から出す
2. スキーマでは、`asOneString(…)` で渡す。見出しは、メッセージをそのまま `parseWith` に渡す。
   ユースケースは、メッセージをそのまま決まりごとの `message` に入れる。スキーマに文を
   文字列で書くと、`schema-messages.test.ts` が失敗し、ユースケースの決まりごとの文を
   文字列で書くと、コンパイルできない
3. 値で変わるメッセージを足したら、`messages.test.ts` の表 `MADE` に、値と、言う文を足す。
   足すまで、テストが失敗する
4. 見出しを言うユースケース、ID を読む関数（`models/<領域>.ts` の `parse…`）、クエリを読む関数
   （`queryDecoder`）を足したら、それぞれの表（`use-case-headlines.test.ts`、
   `id-headlines.test.ts`、`query-headlines.test.ts`）に、行を足す。足すまで、テストが失敗する
5. ユースケースが作る文を足したら、その領域のテストで、決まり（`field` と `rule`）だけでなく、
   言うメッセージも確かめる。フィクスチャーの `saidOfBrokenRules(result)` が、検証のエラーが
   決まりごとに言う文を、順に返す。この確認を守る表のテストはない
6. `shared-i18n` をビルドしてから、`domain` と `api` の型を検査する（パッケージは、ビルドした
   ものから型を読む）

「見つからない」「すでにある」の対象を足すとき:

1. `shared-i18n/src/messages/api/entities.ts` に、名前を両方の言語で足す。持ち主の ID で探す
   ものは、日本語の名前を「この ID の〜」にする
2. エラーを、その名前で作る（`DomainErrors.notFound(entityMessages.<名前>, id)`、
   `DomainErrors.alreadyExists(entityMessages.<名前>, field, value)`）。名前を文字列で書くと、
   コンパイルできない
3. その領域のテストで、エラーを、名前も含めて比べる
   （`toEqual(Result.error(DomainErrors.notFound(entityMessages.<名前>, ID)))`）。`type` と
   `id` だけを比べるテストは、名前の取り違えを見つけない
4. 値で変わる名前を足したら、`messages.test.ts` の表 `MADE` に足す

「いまの状態ではできない」の文を足すとき:

1. 文を、その文が言うものの領域のファイル（`shared-i18n/src/messages/api/<領域>.ts`）に、
   両方の言語で足す。値を言う文は、値を受け取る関数にして、値を、どの言語の文にも、
   そのまま出す。並べ方や、単数と複数は、関数の中で、言語ごとに作る
2. エラーを、そのメッセージで作る（`DomainErrors.conflict(<領域>Messages.<名前>)`）。文を
   文字列で書くと、コンパイルできない
3. その領域のテストで、エラーを、文も含めて比べる
   （`toEqual(Result.error(DomainErrors.conflict(<領域>Messages.<名前>)))`）。`type` だけを
   比べるテストは、文の取り違えを見つけない
4. 値を言う文を足したら、`messages.test.ts` の表 `MADE` に、値と、言う文を足す。足すまで、
   テストが失敗する
5. 画面が、その 409 を、文を読んで見分けていないことを確かめる。文から値を探す画面が
   あるなら、その値は、どの言語の文にも、そのまま出す

画面の文言を足すとき（メッセージにしたパッケージで）:

1. `shared-i18n/src/messages/<だれが言うか>/` に、両方の言語で足す（共通の部品は
   `ui/components.ts`）。値で変わる文は、関数にする。英語の単数と複数は、関数の中で作る
2. 値で変わるメッセージを足したら、そのフォルダーの `messages.test.ts` の表 `MADE` に、値と、
   言う文を足す。足すまで、テストが失敗する
3. 部品は、`useSay` で言う。文を、ソースに日本語で書くと、`src/texts.test.ts` が失敗する
4. 部品のテストに、英語のページで言う文の確認を足す
5. `shared-i18n` をビルドしてから、使う側の型を検査する

アプリの画面に文言を足すとき:

1. `shared-i18n/src/messages/<アプリ>/<領域>.ts` に、両方の言語で書き、`index.ts` から出す。
   新しいアプリのフォルダーは、`package.json` の `exports` と、`vite.config.ts` の入口にも足す
2. 値で変わるメッセージは、そのフォルダーの `messages.test.ts` の表 `MADE` か、カタログの横の
   テスト（`share-links.test.ts`）の表 `MADE` に足す。横のテストで確かめるカタログは、
   `messages.test.ts` の `TESTED_APART` に名前を書く。リンクを含む文は `…WithLink(s)` の部分に、
   区切りの記号は、表 `PUNCTUATION` に書く
3. 領域の書式とフォームの関数は、メッセージを返す。そのテストは、英語の文と日本語の文で比べる
4. 部品のテストと、領域の結合テストに、英語のページの確認を足す

言語を足すとき:

1. `shared-i18n/src/languages/locale.ts` の `Locale` と `LOCALES` に足す。すべての
   `text({ … })` が、その言語の文を書くまで、コンパイルできなくなる。`one-string.ts` の
   `textOfOneString` も、その言語を返すまで、コンパイルできない。`asOneString` に、同じ順で
   その言語を並べる（`one-string.test.ts` が、書いた文が読み戻せることを確かめる）
2. `parseWith` の `ZOD_IN`（言語ごとの、Zod の文）に足す。足すまで、コンパイルできない
3. 契約の `LanguageType` に足して、`pnpm generate` を実行する。足すまで、`sendProblem` が
   コンパイルできない
4. Storybook のツールバーの、言語の名前に足す
   （`frontend/packages/ui/src/__stories__/language.tsx` の `LANGUAGE_NAMES`）。足すまで、
   コンパイルできない
5. 値の書式に足す。`formats/in-each-language.ts` の `inEachLanguage` と、言語ごとに組み立てる
   書式（`dayWithWeekdayOf`、`monthDayOf`、`shortDayOf`、`momentWithWeekdayAt`、`placeOf`）が、その言語を
   書くまで、コンパイルできない

## していないこと

- 文に出る値（状態の名前、プロパティの名前）は、訳しません。契約の値のままです。
- ログの文は、英語だけです。データベースのエラーの `message` と原因（保存してある値が合わない
  ときの、プロパティと決まり）も、そうです。応答には出ません。
- 対象の英語の名前は、書き方をそろえていません（`TreatmentRecord` と `Staff member`）。
  `alreadyExists` の `field`（プロパティの名前）は、訳しません。
- 言語を選ぶ部品は、まだ出していません（[画面の言語](#画面の言語)）。
- メールは、日本語だけです。
- 合う言語がないリクエストを、406 で断ることはしません。既定の言語で返します。
